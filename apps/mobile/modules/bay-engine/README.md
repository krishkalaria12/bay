# Bay engine

Local Expo module imported as `@bay/engine`. The Swift implementation uses the system's `WKWebView`; the Kotlin implementation uses Bay's own Chromium (`org.bay.engine`, from `bay-engine.aar`, built from `engine/android`). Both export `BayEngine` to Expo and the same TypeScript `EngineView`, `Tab`, navigation state and error types. Android has no other engine: `scripts/fetch-android-engine.mjs` installs the engine before a build, and `android/build.gradle` stops without it. `-PbayEngineApiStub=true` compiles the Kotlin against `engine/android/api-stub` instead, to check it builds.

Keep `EngineView` mounted and use its ref to request navigation. `initialUrl` is loaded once when the native view is created (later values are ignored), so a newly mounted tab can open its page before its ref is usable. `load(url)`, `goBack()`, `goForward()`, `reload()` and `stop()` resolve when the native command is dispatched. Observe `onNavigationStateChange` for URL, title, estimated progress, loading and history availability. Main-frame failures are delivered through `onNavigationError`.

Page scripts run in an isolated world on both engines: iOS in a `WKContentWorld` script world (`WKUserContentController`, `defaultClient`), Android in Bay's isolated world in the main frame (`BayTab.evaluate`, through the engine's `__bayPage` messenger, which only Bay's world has). They share the page's DOM, but the page's own scripts can't see them or their state. JavaScript still validates every message before forwarding it (see `parseMediaMessage` and the picker schemas).

File upload (A1): WebKit opens the system picker natively on iOS. On Android the engine asks the view (`BayTabClient.onFileChooser`), which launches `ACTION_GET_CONTENT` with the page's `accept` types through `BayFileChooser` and hands the chosen content URIs back to the page (`BayTab.answerFileChooser`) from the module's `OnActivityResult` handler. One picker at a time; a second request cancels the first.

Video fullscreen (A2): sites' custom players call `element.requestFullscreen()`, which WebKit only honours with `isElementFullscreenEnabled` (set on iOS; native `<video>` fullscreen already worked with `allowsInlineMediaPlayback`). On Android the engine's fullscreen moves the page's own view into the window's decor view (`BayFullscreen`), requests landscape, hides the system bars, and exits on Back via an `OnBackPressedCallback`; leaving puts the view back and restores orientation and bars. Both report through `onFullscreenChange` — always `false` from iOS, where WebKit presents fullscreen itself — and `BrowserScreen` hides the bar and top strip while a tab reports fullscreen. The app follows the system orientation since B10, so Android turns the whole activity sideways for a video and restores whatever was current when it ends.

`onScroll` reports `{ offsetY, deltaY }` in logical screen points, throttled to 50 ms with a trailing update. `pullToRefreshEnabled` defaults to true; both engines reload when the user pulls down from the top. Both support native back/forward edge gestures: WebKit's `allowsBackForwardNavigationGestures` on iOS, and a 24dp edge swipe on Android (`BayPageGestures`) (back from the left edge, forward from the right, armed only when history exists that way, with the page following the finger a little and a haptic at the trigger point). Pull to refresh and edge swipe share the touch path and steal per direction: pulling keeps the gesture once it starts, so a vertical pull from the edge still refreshes.

Long-pressing an HTTP(S) link emits `onLinkPress` with `{ url, title, x, y, image }` instead of the system link menu. Coordinates are normalized within the engine view, or null when unavailable. Android gets the link, its text and any image from the engine's context menu (`BayTabClient.onContextMenu`), in every frame. iOS gets the link from WebKit's context-menu delegate (`contextMenuConfigurationForElement`), whose `linkURL` covers iframes and shadow DOM the old main-frame hit test missed (I4); the title is the URL there, and text selection outside links is preserved. The same event reports a bare image (B13): Android reports a bare image with its own address and `image: true`, while on iOS WebKit exposes nothing for images, so the page (`src/pagescripts/images.ts`) reports long presses through `post({ type: "image", src, title })` after arming itself with `{ type: "image", ready }`; a `ready`-armed view keeps WebKit's own image menu down in the context-menu delegate once a press arrives, and falls back to it when the watcher misses the gesture. `saveImage(url)` saves an image: through the page's own tab on Android (the engine fetches it with the page's cookies, and Bay's downloader shows it), into the photo library on iOS (needing `NSPhotoLibraryAddUsageDescription`).

Share to Bay (B14): `bay://share?url=<encoded>` carries a shared page through the same incoming-link rule (B9); the address itself is always validated as a web URL before a tab opens. Android answers `ACTION_SEND`/`text/plain` on `MainActivity` (filter added by `app.plugin.js`): `BayEngineModule` extracts the first web address out of the shared text, emits `onShare` on `OnNewIntent` for a running app, and `takeShare()` reads the launching intent once for a cold start. iOS uses a share-extension target (`BayShare`, bundle id `<bundleId>.share`): its Swift file and Info.plist live in `share-extension/BayShare`, and `app.plugin.js` wires the target into the Xcode project (node-xcode's `addTarget` plus the build settings and dependency sections it skips). The extension reads the shared web item and opens `bay://share?url=…` through the responder chain, then completes its request. A non-web share (text, image) never opens a tab either way, matching the incoming-link rule.

Quick actions and widgets (B15): `bay://new-tab`, `bay://private-tab` and `bay://search` commands answered by JavaScript through the same incoming-link desk (`bayCommand` in `src/browser/incomingLink.ts`) — a fresh tab, a private tab, or the search card over the current tab. iOS declares `UIApplicationShortcutItems` in `app.plugin.js` and `BayShortcuts` (an `ExpoAppDelegateSubscriber`, registered in `expo-module.config.json`) opens the matching command, cold start included; Android declares static shortcuts in `xml/shortcuts.xml` as `VIEW` intents at the same `bay://` commands, and points `MainActivity` at them with `android.app.shortcuts` meta-data. The search widget opens `bay://search`: on Android an `AppWidgetProvider` (`BaySearchWidget`; the plugin adds its launcher receiver to the manifest; layout, background and provider info sit in the engine's res), on iOS a WidgetKit extension (`widget-extension/BayWidget`), wired as a second `app_extension` target by the same `addAppExtension` helper the share target uses.

Voice search (B16): `startListening()` (an engine module function) listens once and resolves with the transcript, or null when speech or the microphone is denied, there's nothing heard, or no recogniser exists on the device. What it hears lands in the search card's field like a paste (`fill()`); submitting is left as it is. iOS uses `SFSpeechRecognizer` with on-device recognition wherever it exists (asking for microphone and speech permission from the moment of the tap, usage strings from the plugin); Android sends `RecognizerIntent` with the device's language and reads back the first alternative, resolving null rather than falling over on a device with no recogniser.

Page requests (I3, B3, B5, B7): a page's `alert`/`confirm`/`prompt` emits `onPageRequest` with `{ id, kind, message, defaultValue?, url }` and the page waits; `answerPageRequest(id, accepted, value?)` delivers the answer. The server's HTTP sign-in (Basic, Digest, NTLM) arrives the same way with `kind: "auth"` and an optional `realm`, answered with `answerPageRequest(id, true, undefined, username, password)` or `false` to cancel. A link with another app's scheme (`tel:`, `mailto:`, maps, an app link) arrives as `kind: "external"` with `externalUrl`, and accepting opens it through `UIApplication.open` on iOS or an `ACTION_VIEW` intent on Android; the page itself never navigates. A page asking for a device arrives as `kind: "permission"` with `permission: "camera" | "microphone" | "camera-microphone" | "location"`; iOS grants camera and microphone through WebKit's `requestMediaCapturePermissionFor`, while geolocation is WebKit's own system prompt and needs `NSLocationWhenInUseUsageDescription`. Android gets the engine's requests (`BayTabClient.onPermissionRequest`), asks for the system runtime permission first (expo-modules-core's `Permissions`), and grants the page only when both the person and the system allowed it. iOS implements the three `runJavaScript…Panel` delegate methods, `didReceive challenge` for sign-ins, the navigation delegates for external schemes and the media-capture delegate; Android `BayTabClient`'s `onJavaScriptDialog`, `onHttpAuth`, `onExternalUrl` and `onPermissionRequest` (the engine holds each request in `BayTab` by id), and both hold the result until the shared sheet in `src/panels/PageRequest.tsx` answers (dismissing it cancels). Pending dialogs, sign-ins and device requests are cancelled when the view loads or is disposed.

New windows (B19): a page's `target=_blank` / `window.open` used to load in the view that opened it. Both engines now emit `onNewWindow { url, private }` and JavaScript opens a real tab for it in the opener's own session — the opener's page stays. On Android the engine never creates the window itself (`BayTab::IsWebContentsCreationOverridden`); the visible tab is React's own `EngineView`.

Saved passwords (B20): a sign-in answered from the page-request sheet can be kept on the phone in the secure store (one versioned JSON list, `bay-saved-logins`, via `expo-secure-store`, keyed per origin + username — pure format in `src/browser/logins.ts`, IO in `credentials.ts`). When the same origin's server asks again, JavaScript answers the challenge from the store without showing a sheet. A private tab neither reads nor writes this store: its sign-ins stay in its own session. The sheet's save toggle is how a login gets in; it is never filed implicitly. Form-level AutoFill inside pages belongs to the engines' own autofill.

System AutoFill and passkeys in pages (B20): on iOS, WKWebView offers the system's saved passwords in the QuickType bar, suggests strong passwords and saves new sign-ins to Passwords on any site once Bay holds the `com.apple.developer.web-browser` entitlement (B9, claimed with `BAY_DEFAULT_BROWSER=1`); WebAuthn passkeys on any site also need Apple's `com.apple.developer.web-browser.public-key-credential`, claimed by `app.plugin.js` only when `BAY_WEB_PASSKEYS=1` is set as well, because signing fails on an entitlement the provisioning profile lacks. Neither needs a WKWebView setting, and associated domains don't apply to arbitrary sites. Without the entitlements a page still gets the keyboard's Passwords button. On Android, Bay's engine has no autofill or WebAuthn of its own yet (a known gap in `docs/android-chromium-plan.html`); a provider would also only answer once it lists Bay as a privileged browser (Google Password Manager's allowlist is a request to Google). Private tabs keep both: filling and saving belong to the user's password manager, as in Safari and Chrome.

Spaces and folders (B21, local): tabs live in named spaces — the switcher's chips row, like desktop's — each keeping its own last-active tab. Spaces carry a small color palette, and folders (filed from the Tabs menu, like the switcher's filter chips) group tabs inside a space. They persist in `browser.json` (document version 2, which migrates v1 documents into the personal space) and the tab model follows desktop's, so a later sync can map them whole. Cross-device sync itself is not in place yet — it needs the desktop sync native adapters on mobile; pinned sites stay global.

System media controls (I1): `setMediaSession` posts what's playing and `onMediaControl` reports `toggle`/`stop`. Android runs a media notification service (`BayMediaService`); iOS posts Now Playing info and remote commands for the lock screen and Control Center (`BayMedia.swift`, since WebKit doesn't populate the Now Playing center for `WKWebView` media). `useTabMedia` drives both from the page's own media report and keeps private tabs out.

Richer media controls (B17): on top of the I1 play/pause/stop, the mini player's mode (B15's system plumbing) now seeks ten seconds either way (`seekBack`, `seek-forward` buttons) and — for video — a picture-in-picture button that asks the page's video element to leave the page into PiP. The same skip arrives wherever the system has buttons: iOS remote-command skip buttons (`skipInterval` 10) on the lock screen, and Android notification prev/next actions plus the system skip callbacks on the media session. For PiP to work at all, iOS sets `allowsPictureInPictureMediaPlayback` on the engine view and Android declares `android:supportsPictureInPicture` (plus a `pictureInPicture` configChanges entry, so the activity isn't recreated mid-video). When the element can't be put in experiment or the engine won't, the page script reports false and the mini player treats it as a no-op.

`snapshot()` resolves to a unique `file://` JPEG URI in the app cache, or null when no page viewport can be captured. Images are limited to 640 pixels wide. A successful new capture removes only that view's preceding capture. Its last snapshot survives view disposal, so archived cards can retain their image until cache eviction or clear data.

Tab state (B6): `stateKey` (a tab id) restores that tab's last page state before `initialUrl` and saves it as pages finish loading; `saveState()` forces a save (used when the app leaves the foreground and just before a view unmounts). iOS archives WebKit's `interactionState`, which carries back/forward history, scroll position and form text; Android stores the engine's own state (`BayTab.saveState`: each entry's address, title and page state, which carries scroll position and form text). Each tab gets one file under the iOS caches directory or Android's files directory, keys that aren't safe file names are refused, private tabs never write one, and `pruneTabStates(keep)` deletes the rest. A page the system kills has its renderer reloaded once before the error screen. `clearData()` removes these files too.

Module-level `clearData()` waits for native website-data deletion and removes the snapshot cache and saved tab states. Close page views before calling it so scripts cannot immediately write fresh data. Android removes the normal profile's cookies, storage of every kind, HTTP cache and media licences through the engine (`BayProfile.clearData`), and rejects with `E_CLEAR_DATA` when some of it couldn't be removed.

Privacy (both engines): `setContentBlocking(lists, version)` blocks with filter list text through Bay's Rust blocker (`packages/adblock`, Brave's adblock-rust): Android's engine runs desktop Bay's request filter (`//bay/core`) on every navigation, subresource, response and WebSocket of every frame, runs scriptlets at document start, and injects cosmetic CSS (site rules plus generic rules for the classes and ids a page uses); iOS converts the lists into WebKit content-blocking rules, compiled once per `version` and cached by WebKit. `setBlockingPausedHosts` pauses it per site. Addresses the person opens drop tracking parameters (`setTrackingParameters` with `@bay/core`'s `TRACKING_PARAMS`) and move from HTTP to HTTPS, falling back to HTTP for the session when HTTPS can't connect or the site redirects back; local hosts are never upgraded. Third-party cookies are off on both (WebKit's default; the engine's cookie policy on Android). `private` views use a non-persistent data store (iOS) or an in-memory engine profile (Android). The app holds that session while it has private tabs (`setPrivateSessionActive`), since only a few page views stay mounted; it is deleted once the last private tab closes and its views go, and a launch ends one a killed process left behind. Run `scripts/adblock` (part of `pnpm native`) after changing the crate.

The app accepts HTTP and HTTPS addresses. `app.plugin.js` enables HTTP for WebKit page loads and Android's own downloads. Native certificate validation stays enabled; neither engine offers a certificate-error bypass.

Downloads (A3, I2): on Android the engine fetches every download itself, with the page's cookies, so `blob:`, `data:` and POST downloads work like any other (`BayDownloadManagerDelegate`, into the app cache); `BayDownloader`, a data-sync foreground service, shows its progress and moves the finished file into Downloads through MediaStore. On iOS downloads go to `WKDownload` (which is also the route for `blob:` and `data:` there). On iOS 26 each download runs as a continued-processing task (system progress and stop button); older versions get background time. A failed iOS download resumes once from its `resumeData` instead of deleting the partial file, and a finished or failed download posts a notification when Bay isn't on screen (permission is asked on the first download, as on Android).

Run `pnpm native` in `apps/mobile` after native changes. Native build folders are generated; edit this module and its config plugin rather than generated projects. The local package is included in the mobile pnpm workspace and discovered by Expo autolinking.
