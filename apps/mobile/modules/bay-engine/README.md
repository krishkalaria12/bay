# Bay engine

Local Expo module imported as `@bay/engine`. The Swift implementation uses `WKWebView`; the Kotlin implementation uses `android.webkit.WebView`. Both export `BayEngine` to Expo and the same TypeScript `EngineView`, `Tab`, navigation state and error types.

Keep `EngineView` mounted and use its ref to request navigation. `initialUrl` is loaded once when the native view is created (later values are ignored), so a newly mounted tab can open its page before its ref is usable. `load(url)`, `goBack()`, `goForward()`, `reload()` and `stop()` resolve when the native command is dispatched. Observe `onNavigationStateChange` for URL, title, estimated progress, loading and history availability. Main-frame failures are delivered through `onNavigationError`.

Page scripts use a JavaScript bridge, but it is not symmetric: iOS runs them in an isolated script world (`WKUserContentController`, `defaultClient`) the page can't see. Android's system WebView has no isolated worlds, so scripts run in the page's main world behind a token-checked bridge: the bridge is `__bayPage`, the token rotates on each main-frame navigation, and the page can see the bridge's name and the `Symbol.for` state keys but not the token. **This is accepted until our Chromium arrives (A5, phase 7).** A page that finds `__bayPage` still can't call it without the token. Keep page state under `Symbol.for` keys on Android; JavaScript validates every message before forwarding it (see `parseMediaMessage` and the picker schemas).

File upload (A1): WebKit opens the system picker natively on iOS. On Android, `WebChromeClient.onShowFileChooser` forwards to `BayFileChooser`, which launches `FileChooserParams.createIntent()` (falling back to `ACTION_GET_CONTENT` with the page's `accept` types) and delivers the chosen files back through the module's `OnActivityResult` handler. One picker at a time; a second request cancels the first.

Video fullscreen (A2): sites' custom players call `element.requestFullscreen()`, which WebKit only honours with `isElementFullscreenEnabled` (set on iOS; native `<video>` fullscreen already worked with `allowsInlineMediaPlayback`). On Android, `onShowCustomView`/`onHideCustomView` add the player's view to the window's decor view, request landscape, hide the system bars, and exit on Back via an `OnBackPressedCallback`; leaving restores orientation and bars. Both report through `onFullscreenChange` — always `false` from iOS, where WebKit presents fullscreen itself — and `BrowserScreen` hides the bar and top strip while a tab reports fullscreen. The app stays portrait-locked overall (landscape is B10), so a portrait-locked activity keeps fullscreen video letterboxed instead of rotating.

`onScroll` reports `{ offsetY, deltaY }` in logical screen points, throttled to 50 ms with a trailing update. `pullToRefreshEnabled` defaults to true; both engines reload when the user pulls down from the top. Both support native back/forward edge gestures: WebKit's `allowsBackForwardNavigationGestures` on iOS, and a 24dp edge swipe in `BayEngineView` on Android (back from the left edge, forward from the right, armed only when history exists that way, with the page following the finger a little and a haptic at the trigger point). Pull to refresh and edge swipe share the touch path and steal per direction: pulling keeps the gesture once it starts, so a vertical pull from the edge still refreshes.

Long-pressing an HTTP(S) link emits `onLinkPress` with `{ url, title, x, y }` instead of the system link menu. Coordinates are normalized within the engine view, or null when unavailable. Android gets the anchor text through the native focused-node API. iOS gets the link from WebKit's context-menu delegate (`contextMenuConfigurationForElement`), whose `linkURL` covers iframes and shadow DOM the old main-frame hit test missed (I4); the title is the URL there, and text selection outside links is preserved.

Page requests (I3): a page's `alert`/`confirm`/`prompt` emits `onPageRequest` with `{ id, kind, message, defaultValue?, url }` and the page waits; `answerPageRequest(id, accepted, value?)` delivers the answer. iOS implements the three `runJavaScript…Panel` delegate methods, Android the three `WebChromeClient` `onJs…` methods, and both hold the result until the shared sheet in `src/panels/PageRequest.tsx` answers (dismissing it cancels). Pending dialogs are cancelled when the view loads or is disposed.

System media controls (I1): `setMediaSession` posts what's playing and `onMediaControl` reports `toggle`/`stop`. Android runs a media notification service (`BayMediaService`); iOS posts Now Playing info and remote commands for the lock screen and Control Center (`BayMedia.swift`, since WebKit doesn't populate the Now Playing center for `WKWebView` media). `useTabMedia` drives both from the page's own media report and keeps private tabs out.

`snapshot()` resolves to a unique `file://` JPEG URI in the app cache, or null when no page viewport can be captured. Images are limited to 640 pixels wide. A successful new capture removes only that view's preceding capture. Its last snapshot survives view disposal, so archived cards can retain their image until cache eviction or clear data.

Module-level `clearData()` waits for native website-data deletion and removes the snapshot cache. Close page views before calling it so scripts cannot immediately write fresh data. Android uses AndroidX WebKit's `DELETE_BROWSING_DATA` capability and rejects with `E_WEBVIEW_UPDATE_REQUIRED` if the installed system WebView cannot provide complete deletion. It does not claim success through the incomplete legacy API.

Privacy (both engines): `setContentBlocking(lists, version)` blocks with filter list text through Bay's Rust blocker (`packages/adblock`, Brave's adblock-rust): Android checks every subresource in `shouldInterceptRequest` and injects cosmetic CSS (site rules plus generic rules for the classes and ids a page uses); iOS converts the lists into WebKit content-blocking rules, compiled once per `version` and cached by WebKit. `setBlockingPausedHosts` pauses it per site. Main-frame GET navigations drop tracking parameters (`setTrackingParameters` with `@bay/core`'s `TRACKING_PARAMS`) and move from HTTP to HTTPS, falling back to HTTP for the session when HTTPS can't connect or the site redirects back; local hosts are never upgraded. Third-party cookies are off on both (WebKit's default; set explicitly on Android). `private` views use a non-persistent data store (iOS) or a separate WebView profile (Android, `privateBrowsingSupported`), deleted with the last private view. Run `scripts/adblock` (part of `pnpm native`) after changing the crate.

The app accepts HTTP and HTTPS addresses. `app.plugin.js` enables HTTP for WebKit page loads and Android release builds. Native certificate validation stays enabled. Android disables file/content access and mixed content.

Downloads (A3, I2): `http`/`https` downloads go to `BayDownloader` on Android 10+ (a data-sync foreground service saving through MediaStore) and to `DownloadManager` on older versions, and to `WKDownload` on iOS (which is also the route for `blob:` and `data:` there). On iOS 26 each download runs as a continued-processing task (system progress and stop button); older versions get background time. A failed iOS download resumes once from its `resumeData` instead of deleting the partial file, and a finished or failed download posts a notification when Bay isn't on screen (permission is asked on the first download, as on Android). On Android, `blob:` and `data:` live inside the page and never reach the system downloader: the view installs a capture-phase click interceptor (and, for a main-frame jump to a blob, a one-shot fetch) that fetches the bytes in the page and hands them to `BayDownloads.saveBlob` as base64, which writes them to MediaStore with the anchor's `download` name and reports them like any other download (toast, `openDownload`). The base64 crossing the bridge is capped (~50 MB); the download listener's `blob:`/`data:` rejection now means an anchor slipped past the interceptor.

Run `pnpm native` in `apps/mobile` after native changes. Native build folders are generated; edit this module and its config plugin rather than generated projects. The local package is included in the mobile pnpm workspace and discovered by Expo autolinking.
