# Bay for Android (native)

The native Kotlin/Compose rewrite of `apps/mobile` (plan: `docs/mobile-native-plan.html`). minSdk 29, arm64-v8a only.

- Build: `./gradlew :app:assembleDebug` (needs `local.properties` with `sdk.dir`, or `ANDROID_HOME`). `:core:bindings` builds the Rust core with `cargo ndk` and generates its Kotlin API with UniFFI; install `cargo-ndk` with `cargo install cargo-ndk` and use rustup's toolchain.
- Modules use the convention plugins in `build-logic`: `bay.android.application`, `bay.android.library`, `bay.android.compose`. Versions live in `gradle/libs.versions.toml`.
- UI is Compose on Foundation: no Material or AppCompat dependency in UI modules (plan D8).
- Debug installs as `in.krishkalaria.bay.mobile.native`, beside the Expo app; release keeps the store ID.
- Drive the emulator with Argent (`reinstall-app` with the APK, `launch-app` with activity `bay.app.MainActivity`). Root composables set `testTagsAsResourceId`, and controls take `testTag`s equal to the Expo app's `testID`s.
- Words come from the core's catalog through `Strings` (`strings.t("key", mapOf("name" to value))`), never hard-coded text.
- Every Activity calls `window.decorView.announceContentChangesToUiAutomator()` after `setContent` (debug builds only). Compose sends accessibility events only while an accessibility *service* is on, and UiAutomator (Argent, e2e) isn't one, so without this its cache keeps the first frame it read and `describe`/`await-ui-element` see a stale screen.
- The page engine is the `:engine` module (package `bay.engine`), ported from the Expo module (`apps/mobile/modules/bay-engine/android`): `BayEngineView` (a `FrameLayout` over the engine's `BayTab`) reports everything through `onEvent` as one `EngineEvent`, and `Engine` holds what all views share. `MainActivity` is the `EngineHost` (activity, runtime permissions, activity results); `BayApplication` starts the engine and keeps the app out of the engine's child processes.
- It builds against Bay's Chromium (`bay-engine.aar`), installed by `node apps/mobile/scripts/fetch-android-engine.mjs` into the Expo module's `android/engine` folder, which `settings.gradle.kts` reads (`-PbayEngineDir=…` points elsewhere). New engine API (like `BayProfile.forSpace`) needs an `android-engine-N` run first: tag the latest PR #27 head (`android-engine-N`, the next number) rather than working around the missing call, and never commit a local stub.
- Page scripts come from `packages/mobile-pagescripts/resources/pagescripts.json`, an asset of `:engine` shared with iOS (plan D13): run one with `view.runScript(PageScript.WATCH_MEDIA)`, with arguments as a map (`mapOf("seconds" to 10)`). After changing a script in `apps/mobile/src/pagescripts`, run `node packages/mobile-pagescripts/scripts/build.mjs`.
- Native libraries go in compressed (`jniLibs.useLegacyPackaging`): the release APK is about 93 MB instead of 196. If packaging changes, check on a device that the app zygote and the renderer still load `libbay_engine.so` (logcat `nativeloader`).
- Design: `:core:designsystem` (package `bay.design`) holds the tokens (`Radius`, `Space`, `IconSize`, `TextVariant`, `LightColors`/`DarkColors` through `Theme.colors`, `BayIcon` as Material Symbols paths, wallpapers) generated into `BayTokens.kt` by `node packages/mobile-core/scripts/build-design.mjs` from `packages/mobile-core/design/{tokens,icons}.json` (plan D12), Inter, and the components (`BayText`, `BayIconView`, `Modifier.baySurface`, `PillButton`, `BayToggle`, `Modifier.pressFeedback`, `Haptics`). Every screen sits in `BayTheme`. Tokens, not numbers.
- The browser screen is `app/.../browser` (`BrowserModel` over the store, `BrowserScreen`, `PagesHost`, the bar, start page and search card). A button whose icon or text would be read again gets `clearAndSetSemantics { contentDescription; role }` after its `testTag`.
- A freshly booted emulator can ANR any app (System UI and the keyboard included) for a few minutes; check `uptime`'s load and the ANR's process in logcat before blaming Bay.
