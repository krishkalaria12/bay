Bay engineering plan · 13 November 2026 · proposal, no engine implementation in this change

Android on Chromium.
iOS on WebKit.

Build Bay's own Chromium engine for Android on Linux GitHub runners, embed it in the existing Expo app, and keep iPhone pages on system WebKit. This document maps the source changes, build pipeline, data migration, and proof needed to ship that split.

This expands the mobile plan, phase 7. The implementation unit is an Android engine and its native adapter. The shared browser UI, tab model, and iOS engine already exist.

01 Keep the platform boundary explicit

The requested decision is fixed: Android uses Bay's bundled Chromium; iOS uses WKWebView only. The proposed implementation uses Chromium's content/public APIs and a new //bay/mobile embedder. Names marked "proposed" below do not exist in the audited tree.

A successful content_shell_apk proves the compiler and a basic Chromium runtime. It is a test shell, not the finished engine. A content embedder does not provide Chrome's profile services, password manager, default browser UI, permission policy, or download product integration automatically. Those responsibilities must be supplied below.

  • Keep @bay/engine as the shared UI boundary. Implement Android callbacks behind it, with only the explicit API additions in section 7.
  • Ship a self-contained engine with its subprocess services and data. Do not require replacing the phone's system WebView provider or installing a second browser.
  • Do not carry CEF, AppKit, NSWindow, desktop WebUI, or the desktop tab strip into Android. NNCore remains the desktop host.
  • Keep WebKit imports and the iOS Pod dependency graph free of Chromium. iOS still needs its Rust blocker artifact; "WebKit only" refers to page rendering.

04 Prove GitHub runner capacity first

Use Linux x86-64 for Android Chromium compilation. Chromium's build instructions call for at least 8 GB RAM, recommend more than 16 GB, and require at least 100 GB free disk. Cross-building on macOS is unsupported. Upstream build requirements.

GitHub lists standard public Linux runners at 4 CPU / 16 GB RAM / 14 GB SSD, and caps a hosted job at six hours. Disk recovered by deleting installed tools is runner-image-dependent. The earlier "about 90 GB" estimate is not a guaranteed capacity and is below upstream's disk requirement. No build duration or stage count is measured for this Android engine. Runner specifications, job limits.

Gate A · capacity report before engine implementation

Run a manual capacity job on ubuntu-24.04. Measure free bytes and inodes after safe cleanup, source sync / hooks, GN generation, compile / link, compression, artifact download and restore. Budget peak tree plus compressed state plus final artifacts plus toolchains and a measured margin. Record RAM / swap peaks and archive transfer times. A source checkout fitting is insufficient.

If a standard runner cannot complete this cycle, move the engine job to a provisioned Linux self-hosted runner attached to GitHub Actions, or a larger hosted runner if the account supports it. Use storage above upstream's minimum, sized from the report. Do not remove runtime resources to force a fit. App assembly can still run on ordinary runners.

Proposed build pipeline

  1. Resolve. Read a committed Android lock and compute engine identity. Reuse an artifact only for an exact match.
  2. Sync. Fetch direct Chromium at its resolved commit with target_os = ["android"], run its pinned dependency hooks, and verify the version and revision. Pin depot_tools and the privacy patch source. Do not use CEF's automate-git.py for Android.
  3. Generate. Start with target_os="android", target_cpu="arm64", is_debug=false, is_component_build=false, and local compilation with remote execution disabled. Validate every GN argument against the pin. Use low debug information for the capacity proof; establish symbol retention before release.
  4. Prove upstream. Build content_shell_apk, run it on the arm64 emulator / device, and retain the capacity report. Repeat with selected patches. This proof does not produce Bay's AAR.
  5. Build Bay. Apply the shared and Android layers, build the Rust Android static library with a Linux NDK toolchain, then build the new mobile engine and package its AAR plus a small Gradle host APK.
  6. Verify and publish. Install the host APK, validate the final package and provenance, then publish the engine artifact. App builds consume that exact artifact independently of the expensive compile.

Resume behavior to implement and test

Reuse the Linux branch's timed compile and nanosecond-preserving zstd archive utility after review. Use a stable absolute engine root, separate Android / ABI state names, versioned state metadata and archive checksums. Keep SDK / NDK / JDK outside the archived tree where possible, reinstalling the exact versions on each runner.

  • The existing Linux cleanup deletes /usr/local/lib/android and /usr/lib/jvm. Write an Android-specific cleanup that preserves or deliberately reinstalls the required toolchains. Do not invoke scripts/linux/ci-disk.sh unchanged.
  • Use explicit stage dependencies or a serial controller. A matrix with max-parallel: 1 is not a dependency chain. Reserve measured time for compression and upload before the six-hour limit; a forced kill cannot save state.
  • Distinguish success, deliberate pause 124, compile failure and cancellation. Preserve state and logs after a genuine compile error, then fail the run. Retain the reference workflow's explicit !cancelled() archive / upload conditions and verify them with an injected compile failure; do not replace them with ordinary success-only steps.
  • Verify restored revision, toolchain, GN args, patch baseline and source identity before resuming. An unchanged identity can resume directly. A changed patch requires a clean base and reapply; reuse compatible build outputs only after proving the invalidation logic. Never compile stale patched sources under a new artifact ID.
  • Preserve symlinks and timestamps, check the archive lives outside the tree, and verify a restored no-op build performs no unexpected full rebuild. Track the larger peak required while downloading and extracting state.
  • Restrict state reuse to trusted builds from this repository and the intended workflow / branch. Do not execute build files restored from untrusted PR artifacts. Names alone do not establish trust.
  • End with a required final job that checks the engine artifact exists for the requested ID and passed smoke tests. Exhausting stages after pauses must fail, even if individual stages exited successfully.
  • Use Actions artifacts for transient checkpoints with bounded retention. Check actual account storage and transfer feasibility; do not assume the dependency cache can store a Chromium tree. Final engine releases and build-state archives have separate retention policies.

Artifact manifest Publish engine.json with artifact ID, engine API schema, exact revisions, GN args digest, toolchain versions, ABI list, minimum Android API, runtime file inventory and SHA-256 hashes. Include license / notice files and keep symbols / mappings separately with matching native build IDs.
ABI and platform compatibility Start with arm64-v8a, matching the app and this Mac's emulator. If Linux emulator CI needs x86_64, build a separate x64 engine and every other native dependency; never claim one arm64 APK proves x64. Set minimum API to the higher of the Chromium pin and Expo requirements and verify merged app metadata.
Packaging checks Validate ELF and APK alignment and run on 16 KB pages. Verify all native dependencies, including React Native / Skia and Rust. Check uncompressed native-library loading, JNI symbol registration, resource shrinking, child services, R8 mapping and bundle-generated APKs. Preserve locales, codecs and GPU fallback resources selected by the supported configuration.

Main's macOS source setup pins CEF 564dd6c4aafff558154bd3176eb5d13551db6734. The Linux reference lock reports Chromium 154.0.8037.58. Resolve the actual Chromium commit associated with the intended desktop baseline and record it directly in the new Android lock; the CEF commit and a Linux sysroot metadata commit are not interchangeable Chromium source pins. Review security freshness when implementation starts. "Same pin as desktop" is a compatibility starting point, not permission to ship an outdated engine.

The AAR packaging method is an early research gate. Inspect the pinned tree's Android GN templates, JNI generation and content-shell packaging, then choose the smallest supported export path. If it needs companion artifacts, declare and version them explicitly. There is no existing bay-engine.aar target in this repository.

Android's 16 KB page-size guidance covers both ELF and APK alignment. Chromium's native-library packaging notes explain why loaders, JNI and subprocess data must be considered together.

08 Keep app data, version engine data

The shared JSON tab / space / preferences model is not a Chromium profile. Keep it intact. WebView cookies, storage and saved Android Bundle history cannot simply be copied into a Chromium browser context.

Data Migration / rollback behavior
Tabs, pins, history, spaces, preferences Preserve the existing store schema. Reopen normal tab URLs through the new engine. Include background tabs, archive / restore and no-page start tabs in the upgrade fixture.
Normal cookies and site storage Use a new versioned Chromium profile directory. Plan for site sign-in to be required again; do not promise transparent cookie or IndexedDB migration. Show a one-time Android engine upgrade notice before switching and preserve old data until rollback policy is settled. Never merge private cookies into normal state.
Saved native tab state Use engine-tagged filenames / directories and a versioned envelope. Detect old WebView bundles, ignore them for Chromium, and open the saved URL. New Chromium states must not be read by a WebView build. Preserve unsupported state separately until cleanup is explicitly allowed by the migration version.
Private tabs and generated previews Close / discard old private sessions during upgrade; do not import them or create private state files. Inspect snapshots, notifications, logs and crash metadata for private-page details. Files the user explicitly saved to Downloads are user exports and follow the existing product policy, not silent browser-data deletion.
Downloads and secure-store logins Keep saved content URIs, download metadata and HTTP credentials compatible. Preserve DownloadUpdate identifiers / reference lookup or migrate them explicitly. Verify an old finished download still opens and old private records stay out of persistent lists.
Clear all website data Close live pages, stop requests and clear the active Chromium contexts asynchronously, then remove tab states and snapshots. If legacy WebView data is retained for rollback, the clear-data action must also delete it and mark it unavailable for restoration. A later rollback must not resurrect data the user cleared.

Rollback is a rebuilt, signed Android app using the previous compatible engine selection, with a higher store version code where needed. It is not an executable download or a silent runtime switch back to system WebView. Never open a newer Chromium profile with an older incompatible engine; use an isolated profile and retain the shared tab URLs. Reverting a code commit alone is not a data rollback.

11 Separate engine compilation from app releases

  1. Build / test an engine on the new explicit Android engine workflow, then publish an immutable prerelease asset set keyed by Android engine ID. The job that publishes needs narrowly scoped release write access; build and fetch jobs remain read-only. Avoid release URLs that select "latest."
  2. Open a small app dependency update changing android-engine.json, verify fetch and native parity, then produce preview APK / production AAB with the existing EAS workflow. The CI runner currently submitting EAS does not itself assemble the app. Keep iOS IPA builds separate from the Linux engine compile.
  3. Validate generated device APKs from the AAB, all declared ABIs / supported API levels and 16 KB runtime. Keep licenses, resource inventory, R8 mapping and matching native build IDs / symbols with the release.
  4. Roll out to internal testers before Google Play testing tracks. iOS ships the same shared feature behavior on WebKit. Store signing remains in the existing credentials setup, with no secrets committed into the engine lock.
  5. With bundled Chromium, Bay owns engine security updates. Monitor upstream fixes, update pins / privacy patches, rebuild the full tested artifact, and ship an app update. Do not wait for a desktop feature release when an Android security fix is needed.
  6. Keep the previous compatible engine artifact and signed app inputs for rollback; rehearse the profile isolation rules from section 8. Never let artifact expiration make a released app impossible to rebuild.

The broader mobile plan originally allowed an initial system-WebView release before phase 7. This document defines the requested Chromium destination. During implementation, label any legacy preview explicitly. The Chromium release gate cannot be marked complete with a system-WebView APK, and no runtime fallback should hide an engine startup failure.
