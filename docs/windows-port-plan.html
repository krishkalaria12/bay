Bay for Windows

On Windows, Bay's UI is drawn by the engine itself. The React UI runs as a privileged Chrome page, each tab is an element inside that page, and one compositor draws both, the same model Zen uses on Gecko. The engine is the one the Mac already runs: Chrome plus Bay's layer. This plan covers what carries over, the architecture, the phases in order, and what was removed from the earlier React Native for Windows design.

Revised 17 October 2026. The hosting decision moved from React Native for Windows to a web-rendered UI. The React Native for Windows host, its native-module glue and its JavaScript animation engine have been removed from feat/windows; any of it can be recovered from commit f9e87f27. The portable C++ (sync, import), the engine build and the packaging stay. See What changed and the implementation status.

Summary

Bay on Windows is Chrome with Bay's UI as its window. Bay's React UI is built with react-native-web and served as a Chrome WebUI page (chrome://bay). Each tab is an <embed> in that page, backed by Chromium's SurfaceEmbed. The window is a Views widget created through the same BrowserWindow hook the Mac's NNCore already uses. Native calls travel over one Mojo interface carrying the JSON contracts Bay already generates.

Upstream is building the same thing. Chromium's WebUI Browser (feature kWebium, chrome/browser/ui/webui_browser) renders a whole browser window as WebUI and hosts tab contents through components/surface_embed. Both are in Bay's pinned tag, 154.0.8037.58, switched off by default, and under active development (about 100 commits to the window code since June 2026). Upstream's SurfaceEmbed render test runs on Windows and macOS; it is disabled only on Linux.

Why this beats the earlier design. React Native for Windows could not draw over web pages in one window (the airspace rule), so the earlier plan's first open item was a host for overlays above Chrome's windows. Here overlays are ordinary DOM above an <embed>. Bay keeps real Reanimated (its web path) instead of a custom animation engine, and Windows and Linux share one host.

What it costs. The UI has to reach parity under react-native-web, the 26 synchronous native calls become asynchronous, and Bay depends on an upstream feature that is still experimental. Phase 2 is a short spike that tests every one of these on a Windows machine before the main port.

Phase 0 still runs entirely on this Mac. Booting the UI on the web, splitting NNCore's .mm files and the async bridge all happen here, and none of them change how the Mac app behaves.

The architecture

The window

Chrome creates browser windows through BrowserWindow::CreateBrowserWindow. With kWebium on, it returns a WebUIBrowserWindow: a views::Widget whose client view is a views::WebView loading the WebUI. Its client view turns CSS app-region: drag areas into HTCAPTION, and permission prompts anchor to elements the WebUI reports. NNCore already replaces window creation on macOS (g_bay_browser_window_factory in browser.cc, creating NNBrowserWindow). On Windows the same hook creates BayWebUIBrowserWindow, modelled on upstream's window but loading chrome://bay. Upstream keeps the standard Windows frame, so Bay adds its own frame view: caption buttons drawn by the UI, the maximize button reported as HTMAXBUTTON, and resize borders.

The UI

The React tree in apps/browser/src builds for the web with Metro (Expo 54) and is served by a WebUIDataSource. The data source sets the CSP: object-src 'self' for the embeds, a policy for react-native-web's injected styles, and Trusted Types (OverrideContentSecurityPolicy, or DisableTrustedTypesCSP while the bundle needs it). React Native's platform props map to the DOM in @bay/platform's .web.tsx wrappers: hover to pointer events, tooltips to title, the focus ring to :focus-visible, window dragging to app-region: drag.

The tabs

SurfaceEmbed embeds an independent WebContents in a WebUI through a blink::WebPlugin. The browser owns the tab's WebContents, so a tab can be detached and re-attached to another window without reloading, which is how NNCore already treats tabs (transfer and adoption). The UI asks the engine for a tab's SurfaceEmbedHandle id and renders <embed data-content-id>. Input, focus and Tab traversal, accessibility tree stitching, hit testing and visibility are in M154. The fix that stops forcing the surface opaque, pinch zoom and occlusion landed after it and come in as backports.

The bridge

The earlier Windows bridge already reduced every native module to invoke(module, method, argsJSON) plus events, with contracts generated from the TypeScript facades. That shape moves to Mojo unchanged: a bay.mojom.NativeHost interface bound only for chrome://bay, dispatching to NNCore's JSON engine calls (NN_ENGINE_CALL) and to Windows services. Mojo's sync methods are only synchronous when called from C++, so from the UI page every call is async: the 26 sync methods become async, a snapshot, or optional.

The engine

NNCore is Chrome plus Bay's layer; it runs no CEF at runtime. About 9.2k of its 10.1k .mm lines are Chrome C++ with less than 10% Objective-C, so Phase 0 splits them into portable .cc and small _mac.mm files, and Windows builds the same engine. chromium-bay-layer-win.patch already links Bay's layer into chrome.dll. The Windows build target changes from libcef to chrome, which is how ungoogled-chromium-windows and Helium build.

Fallbacks

If Phase 2 finds Then
SurfaceEmbed fails on Windows (input, IME or painting) Use upstream's other path in the same window, GuestContents through an iframe (webview.html.ts switches on enableSurfaceEmbed), or the Linux plan's L‑A: tab BrowserViews under a transparent overlay view with a masked hit test
The UI can't keep 60 fps Profile first (compiler output, layout thrash, Reanimated's web path); move hot animations to CSS transitions
Blur over pages doesn't work Translucent panels without blur, as Zen ships on Linux; or a Views layer background blur under the panel rects

Why not CEF for this. A WebUI browser window and SurfaceEmbed live at Chrome's BrowserWindow and tab-strip layer. CEF's Chrome style wraps that layer in its own browser view and hides the WebContents. Bay already maintains a Chrome-level engine for macOS, so using it on Windows removes a second engine instead of adding a third layer.

Phase 0

Groundwork on macOS

Runs on this Mac, shared with Linux

Leave the codebase ready for a web-hosted UI without changing the Mac app.

Depends on
Nothing
  • Boot the UI on the web. Build apps/browser for the web with Metro (Expo 54) and open it in desktop Chrome against stub native modules. List every react-native-web gap: layout, text, macOS-only props, Reanimated's web path.
  • Web wrappers. .web.tsx versions of the @bay/platform views: hover → pointer events, tooltip → title, focus ring → :focus-visible, draggedTypes → HTML5 drag, mouseDownCanMoveWindow → app-region: drag.
  • Platform identity. On the web Platform.OS is "web". The host passes the real OS in its constants, and @bay/platform maps it to windows or linux for capabilitiesFor and the shortcut tables.
  • No sync calls. Convert the 26 synchronous native methods to async, snapshots pushed by the host, or optional. This also simplifies the Mac bridge.
  • Transport-agnostic bridge. Keep the {value}/{error} envelopes and generated contracts; put a transport interface under them so a Mojo transport can replace the TurboModule one.
  • Split NNCore. Move the Chrome logic of each .mm into a .cc and keep AppKit in a small _mac.mm, starting with nn_browser, nn_browser_window, nn_tab_info and the prompts.

Exit criteria

  • The full UI renders in desktop Chrome on the Mac against stubs, with every gap triaged.
  • No synchronous native call remains in the contracts.
  • The Mac app builds and passes its acceptance scripts after the NNCore split.
Phase 1

Windows toolchain & engine build

Needs a Windows machine

Build Chrome from Bay's pinned tree on Windows x64, with Bay's patches and layer, and run upstream's WebUI browser on it.

Depends on
The series platform column (done); Phase 0 is helpful, not blocking
Machine
Windows 11 x64; at least 100 GB free on an NTFS SSD; 32–64 GB RAM is realistic; as many cores as possible. A cloud VM works.
Toolchain
The Visual Studio and Windows SDK named by Chromium 154's windows_build_instructions.md, with "Desktop development with C++" and MFC/ATL; Python 3, Git, depot_tools; long paths enabled.
  • Run the existing download and patch steps (scripts/windows/engine.py), then build the chrome target instead of libcef. ungoogled-chromium-windows and helium-windows are the references for an ungoogled Chrome build on Windows.

  • Upstream's WebUI browser runs on it with SurfaceEmbed tabs.
  • Engine artifacts are archived and versioned.

Phase 3

Engine: NNCore on Windows

Windows

Bay's engine runs on Windows with its own window, WebUI and tab strips, and the CEF host is retired.

Depends on
Phases 0 (NNCore split) and 2
  • //bay/core builds into chrome.dll on Windows; NNMainDelegate and the NNCore hooks apply on Windows.
  • BayWebUIBrowserWindow: a BrowserWindow modelled on upstream's, reusing its modal dialog host, exclusive access (fullscreen), find bar owner and side panel pieces from chrome/browser/ui/webui_browser.
  • chrome://bay: a WebUIController with its data source and CSP, the SurfaceEmbed binder and plugin allowlist for Bay's URL, and the bay.mojom.NativeHost receiver.

  • Retire the CEF host: engine/nncore/src/bay/core/win, the CEF targets in engine.py, and the CEF-only patches on Windows.

Exit criteria

  • The Windows build opens Bay's window with real tabs, extensions, passwords and DevTools, and no CEF binaries ship.
  • The Mac app still builds and passes its acceptance scripts.

Phase 6

Data: import, sync, secrets

Parsers & vectors on Mac Integration on Windows

A user moving from Chrome, Edge or Arc on Windows lands in Bay with their data, and a Mac user's sync folder opens on Windows.

Depends on
Phase 4 for integration; the C++ already exists and has tests
  • Compile packages/sync/windows and packages/import/windows into the Bay layer and expose them as BaySync and BayImport on the Mojo bridge. Long work runs off the UI thread, and imported cookie and card values stay in the browser process.
  • Crypto: keep CNG on Windows, or move the sync crypto to the BoringSSL already in Chrome so Windows and Linux share one backend. The golden vectors decide either way.
  • Chromium secrets: older v10 data is DPAPI-protected and importable with consent. App-bound encryption (Chrome 127+) ties cookies to Chrome's own service; Bay does not work around it and guides users through Chrome's password export instead.
  • Folder sync with OneDrive placeholders, Dropbox and SMB shares; the key store in Credential Manager or DPAPI.

Exit criteria

  • The import fixtures give identical results on Windows.
  • A vault written on the Mac opens on Windows and the other way round.
Phase 7

Packaging, signing, updates

Windows + CI

A signed per-user install that updates itself, without SmartScreen warnings.

Depends on

  • Installer: the existing Inno Setup script (packaging/windows/Bay.iss), per-user under %LOCALAPPDATA%, staging the Chrome build instead of the React Native app.

Phase 8

Hardening & beta

Windows + VMs

Quality on par with the Mac app, then a limited beta.

Depends on
Phases 5–7
  • Accessibility with Narrator and NVDA across the UI and pages; keyboard-only use; high contrast.
  • Displays: mixed DPI, 4K at 150–200%, HDR video.
  • GPUs: Intel, AMD, NVIDIA; DirectComposition and transparency quirks; Windows on Arm, then a native arm64 build.
