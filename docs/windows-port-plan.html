Bay for Windows

Bay can ship on Windows without starting over. The React UI, the TypeScript packages and most of the Chromium patch series carry over. What has to be built for Windows is the native layer under the UI. This plan says what moves, what gets rebuilt, the one architecture question to settle first, and the phases in order. macOS-only features such as Liquid Glass, the Metal shaders and the Dock tile are deliberately left out.

Drafted 8 Oct 2026 Engine: CEF/Chromium 154.0.8037.58 UI: React Native 0.81 · Expo 54 · Reanimated 3.19

Implementation checkpoint, 17 October 2026. Shared desktop code, typed contracts, Windows source and build tooling are present. Native service coverage and the Windows hosting gate remain incomplete. See the implementation status and validation commands.

Summary

Yes, Bay can run on Windows. The approach: keep one React codebase and run it on React Native for Windows. It uses the New Architecture (Fabric), which is the only option since 0.82, and its 0.81 line matches Bay's RN version. The CEF/Chromium engine gets rebuilt for Windows with the same patch series, and the macOS native layer is rewritten in C++ against Win32 and the Windows App SDK.

About 46k lines of UI TypeScript (apps/browser/src), @bay/core, every package's TypeScript API, and most of the 45 engine patches can be reused. About 45k lines of Swift, Objective‑C++ and Metal can't. Half of that is engine/nncore plus packages/nncore/ios, which host Chrome's tabs inside AppKit views.

One question decides how much of the macOS design survives: can React UI draw over web pages in a single Windows window? On macOS, NSView layering makes this trivial. On Windows, every pixel belongs to exactly one HWND (the "airspace" rule), and Chrome draws into its own HWND. Phase 2 is a short spike that answers this before the expensive work starts.

Building the engine on Windows needs a Windows machine with a lot of disk and RAM. As agreed, that can wait. Phase 0 runs entirely on this Mac and leaves the codebase ready for the Windows work without changing how the Mac app behaves.

Scope

In scope for the first Windows release

  • Everything in the sidebar and tabs model: spaces, pinned and split panes, command panel, find bar, downloads, settings, developer mode bar and inspector
  • Chrome features through the engine: extensions and the Web Store, passwords and autofill, permissions, PiP, casting, DevTools, site settings, history, bookmarks
  • Content blocker, favicons, zoom, profiles
  • Importing from Chrome, Edge, Brave, Vivaldi, Opera, Firefox and Arc for Windows
  • Encrypted folder sync, readable by the Mac app and the Windows app
  • Installer, auto-update, code signing, default-browser registration

Out of scope (macOS-only)

  • Liquid Glass (BayGlassEffect) and NSVisualEffectView vibrancy, replaced by Mica/Acrylic where it fits
  • Metal shaders: area light, edge light, power-up and the grained OKLab backdrop (@bay/shaders)
  • Dock tile plug-in, Dock selection, alternate app icons
  • AppleScript dictionary (Bay.sdef), Handoff, Apple Translation
  • Touch Bar autofill and iCloud Keychain passkeys
  • Importing from Safari and Dia, which uses Apple Events
  • Calendar via EventKit (can return later through Windows APIs)

Already in our favour

  • nn_engine.h is already plain C with JSON arguments, looked up with dlsym. On Windows it becomes GetProcAddress on chrome.dll, and passwords, history, bookmarks, cookies, site settings, downloads, zoom and search engines carry over with no API change.
  • The JS never branches on Platform.OS today, so adding the seams is a clean job.
  • nativeApi.tsx already uses requireOptionalNativeModule, so the app handles a module that's missing.
  • Chrome runs Windows natively (Aura/Views), so prompts that Bay leaves to Chrome's Views work unchanged.

Working against us

  • Expo Modules has no Windows target. All 27 named native modules and views go through requireNativeModule / requireNativeViewManager from expo-modules-core.
  • Reanimated is everywhere: 232 Animated.View, 172 useAnimatedStyle, 53 runOnJS, 39 measure. I found no confirmed Windows support.
  • NNCore.h is an Objective‑C API (NNCoreEngine, NNCoreWindow, NNCoreTab + delegates), so a Windows host can't call it.
  • macOS-only RN props are used widely: onMouseEnter (19 files), keyDownEvents (14), enableFocusRing (14), tooltip, drag and drop. ⌘ appears in 39 files, and Symbol in 74.

The hosting decision

How macOS works today (from the patches): Chrome's own window is the app window (CefBrowserSettings.client_window). Chrome shows no tab strip or toolbar in it and keeps it open with no tabs. The RN root view is a subview of Chrome's BridgedContentView and gets hit testing and accessibility first (bayEmbeddedView, chromium-window-hosted.patch). Each tab's RenderWidgetHostViewMac stays out of Views (NativeHostedContents, chromium-webview-native-hosted.patch), and the app places it wherever a pane is. AppKit composites everything together.

Why Windows is different: Chrome on Windows draws a whole top-level window into one HWND through DirectComposition. Tab contents are Aura windows, not separate native views an app can move around. An HWND owns its pixels, so another technology can't blend semi-transparently over them. Since Windows 8, child windows can be layered, and DirectComposition can target child HWNDs, which opens some room.

Ruled out: off-screen rendering into a composition surface (CEF OSR with shared D3D textures). CEF's windowless mode is tied to Alloy-style browsers. Bay depends on Chrome style (tab strip model, extensions UI, Chrome's prompts), so OSR would cost those features. This comes from CEF's runtime split; confirm it against the CEF 154 headers in Phase 1.

Phases run in order unless noted. Phase 2 is a go/no-go gate: Phases 3–5 depend on which hosting option it picks. Phases 3 and 4 can run in parallel once it passes, and so can 5 and 6. Each phase shows where it can run, because the Windows machine comes later.

Phase 0

Groundwork on macOS

Runs on Mac, now

Make the shared code platform-neutral and pin down every native contract, so the Windows work becomes "implement this interface" rather than "find out what the Mac does". The Mac app must behave exactly as before.

Depends on
Nothing
Touches
apps/browser/src, packages/*/src, engine/nncore, engine/patches/series*, CI

JS / TS

  • Add one platform module (isMac, isWindows, capabilities) and route every macOS-only call through it, never through scattered Platform.OS checks.
  • Keyboard: a Mod abstraction (⌘ on Mac, Ctrl on Windows) for menuShortcuts, keyDownEvents, shortcut labels (⌘ in 39 files) and recordShortcut. Write the Windows shortcut table (Ctrl+T, Ctrl+L, Ctrl+Shift+T, Alt+←/→, F5/Ctrl+R, Ctrl+1–8, Ctrl+Tab…).
  • Split @bay/shell exports into core (windows, commands, clipboard, files, dialogs, menus) and mac extras (Dock, AppleScript, Handoff, Translate, Calendar, app icons, intro music), with the extras optional.
  • Fallbacks for GlassEffect, VisualEffect and the four shader views: a plain Surface with theme colours whenever the capability is missing.
  • Icons: change Symbol to take a Bay icon id, and keep a table of SF Symbol name ↔ Fluent icon name. Do this now, while the full list is easy to extract from 74 files.
  • Wrap macOS-only RN props (enableFocusRing, tooltip, draggedTypes, mouseDownCanMoveWindow) in small components. RNW then gets equivalents in one place, not 50.

Native contracts & engine

  • Write a typed spec for each of the 27 Expo modules and views (methods, events, view props). Generate the RN codegen spec from it so a Windows TurboModule can be checked against the same contract. Extend test-native-stub.mjs to assert that the stubs match the spec.
  • Write a C API for NNCore (nncore_c.h) in the style of nn_engine.h: opaque handles, JSON arguments, a callback sink. Turn the ObjC NNCore.h into a thin wrapper over it. Then the Mac host and the Windows host share one engine surface.
  • Move the platform-free logic out of the .mm files (nn_seams, nn_devtools_call, nn_extension_view, nn_installed_bubble, nn_desktop_capture, nn_host_visibility and others with no Cocoa) into .cc. Leave only the AppKit code in _mac.mm.
  • Add a platform column to engine/patches/series (all / mac / win) and teach series.py to skip what doesn't apply.
  • CI: run pnpm typecheck and pnpm test on a windows-latest runner. They're pure Node and cheap, and they catch path and line-ending assumptions early.
  • Port the build scripts that must run on Windows (scripts/download-engine, engine-build, apply.sh) to Node or Python, which runs on both.

Exit criteria

  • The Mac app passes the existing test scripts (shortcuts, windowing, hover-shift, tab-drag, zoom-scroll) unchanged.
  • No macOS-only module is imported without a capability check.
  • Every native module has a written spec, and the stubs are checked against it.
  • The Mac host uses nncore_c.h, and NNCore.h is only a wrapper.
  • JS checks are green on Windows CI.
Phase 1

Windows toolchain & engine build

Needs a Windows machine (deferred)

Get the same CEF/Chromium 154 tree, with Bay's patches, building and running on Windows x64.

Depends on
Phase 0's series platform column and the cross-platform scripts (helpful, not blocking)
Machine
Windows 10/11 x64; at least 100 GB free on an NTFS SSD (more for CEF plus a second output directory); Chromium asks for 8 GB RAM minimum and recommends more than 16 GB, and 32–64 GB is realistic for builds of this size; as many cores as possible. A cloud VM works.
Toolchain
The Visual Studio release named by Chromium 154's windows_build_instructions.md. Current docs ask for VS 2026, older ones VS 2022: read the one at our pinned revision. Install "Desktop development with C++" with MFC/ATL and the Windows 11 SDK version it lists. Add Python 3, Git and depot_tools.
  • Run the download script on Windows (the 154.0.8037.58 pin), then CEF's patch-and-gen, ungoogled-chromium, domain substitution and our series, in the macOS order.
  • Use ungoogled-chromium-windows as the reference for the Windows-specific ungoogled steps (it builds without Google's prebuilt binaries).
  • chromium-bay-layer.patch adds //chrome/browser/bay:exports next to //chrome/browser/mac, which is the macOS framework target. Add the Windows equivalent in the chrome.dll target, and write a .def or __declspec(dllexport) list for the nn_* exports.
  • Run the GN args: is_official_build, target_cpu="x64", symbol level, and the CEF Chrome-style flags. Add an arm64 output directory later.
  • Build cefclient/cefsimple with the patches and click through tabs, extensions, passwords and DevTools.
  • Confirm the CEF facts the plan relies on: Chrome style vs Alloy for windowless rendering, external_message_pump vs multi_threaded_message_loop on Windows (the latter is Windows/Linux-only), and Views-hosted Chrome-style windows.
  • Archive the engine build output (headers, .lib, chrome.dll, resources, PDBs) so the app build can download it, not rebuild it.

Exit criteria

  • The patched engine builds reproducibly from a clean checkout, using one documented command.
  • A patched cefclient runs Chrome-style tabs with an extension installed from the Web Store.
  • Engine artifacts are archived and versioned.

Phase 6

Data: import, sync, secrets

Parsers & vectors on MacIntegration on Windows

A user moving from Chrome, Edge or Arc on Windows lands in Bay with their stuff, and a Mac user's sync folder opens on Windows.

Depends on
Phase 4's module layer for integration; the parser and crypto work can start any time

Import

  • Port the browser-agnostic readers: Chromium bookmarks, history, autofill, extensions and sessions; Firefox places, plus logins via NSS key4.db; Netscape HTML; passwords CSV; zip. Find Windows profile paths for Chrome, Edge, Brave, Vivaldi, Opera, Firefox and Arc for Windows (a packaged app under %LOCALAPPDATA%\Packages).
  • Chromium secrets on Windows: older data (v10) is AES‑GCM under a key in Local State protected by user DPAPI, which Bay can decrypt with the user's consent. Since Chrome 127, app-bound encryption ties cookies to Chrome's own elevation service and checks the caller's path. Google has said passwords and payment data would follow. Bay must not try to get around that. Plan: don't import cookies from Chrome; import passwords directly where they're still DPAPI-only, and otherwise walk the user through Chrome's password CSV export (PasswordsCSV.swift already handles that format).
  • Decide on language: rewrite in C++ (simplest toolchain) or keep the Swift Core and build it with Swift for Windows (Arc's route), using swift-crypto for CryptoKit. Decision needed.

Sync

  • Re-implement SyncCrypto/SyncVault (AES‑GCM, HKDF, HMAC‑SHA256) with Windows CNG or the BoringSSL already in the engine. Generate golden test vectors from the Swift tests on Mac now, and require byte-identical output on Windows.
  • SyncKeyStore moves from Keychain to Credential Manager/DPAPI. The recovery phrase and wordlist stay unchanged.
  • Folder sync on Windows: check OneDrive Files On-Demand placeholders (files that aren't downloaded yet), Dropbox, and SMB shares for file-locking differences.

Exit criteria

  • The import fixtures in packages/import/fixtures give identical results on Windows.
  • A vault written on Mac opens on Windows and the other way round, using one shared fixture.
Phase 7

Packaging, signing, updates

Needs Windows

A signed per-user install that updates itself, without Defender SmartScreen scaring people off.

Depends on
Phase 4 (an app to ship); the signing account can be set up any time
  • Installer: per-user under %LOCALAPPDATA%, no admin rights (like Chrome's user-level install). Choose between a Velopack-style setup (installer + deltas) and a WiX/NSIS installer paired with WinSparkle (same appcast model as scripts/release.sh). MSIX is an option, but its container rules complicate browser registration and native messaging.
  • Registration: RegisteredApplications, StartMenuInternet\Bay\Capabilities, ProgIDs for http/https/.html/.pdf, an AUMID for notifications, Start menu shortcut, uninstaller entry; native messaging host keys under HKCU\Software\Bay\NativeMessagingHosts.
  • Signing: Azure Artifact Signing (formerly Trusted Signing) costs about $9.99/month for 5,000 signatures. It's available to individuals and organisations in the US and Canada, and to organisations in the EU and UK, and it issues no EV certificates. Otherwise, buy an OV/EV certificate from a CA. Sign every PE file: Bay.exe, chrome.dll, helpers, the installer.
  • Release script: a Windows counterpart of scripts/release.sh producing the installer, update package and appcast entry, with notes from the same release-notes/<version>.md.
  • Crashes: Chromium's Crashpad already writes minidumps. Point crashReports at Bay's crash directory instead of macOS DiagnosticReports, and archive PDBs for every release.

Exit criteria

  • A clean Windows 11 VM installs, launches, sets itself as default through Settings, updates to the next build and uninstalls cleanly.
  • SmartScreen shows no unknown-publisher warning for a signed build.

Risks

Risk Impact Mitigation
RN can't draw over Chrome in one window (airspace) High Phase 2 gate before any big spend; fallbacks B and C already planned
Reanimated doesn't run on RNW Fabric (the old RNW request #4151 is closed with no confirmed support) High Test in Phase 2; a lib/motion wrapper keeps the 232 call sites unchanged
Expo Modules has no Windows target Medium Phase 0 specs + codegen; a small shim or .windows.ts resolution
RNW trails React Native (0.84 vs RN's current line) and has fewer contributors; Fabric component bugs (DPI scaling #16383, orphaned islands breaking input) Medium Pin RNW 0.81 to match RN 0.81; budget time to send fixes upstream; keep the Fabric components we depend on few
CEF external message pump on Windows (nested loops are a known weak spot) Medium Re-validate cef-idle-pump/cef-pump-wake in Phase 3; drive modal loops (menus, dialogs, window drag) on purpose in tests
Chrome's app-bound encryption blocks cookie and password import Medium No cookie import from Chrome; CSV fallback for passwords; never work around it
Engine build cost (disk, RAM, hours per build); can't build on the current Mac Medium One large VM; archive artifacts; rebuild only when the pin or patches change
Two platforms to keep in sync with every Chromium rebase Medium Platform column in series; Windows CI on every engine bump; keep platform code in _mac/_win files, not #if soup
SmartScreen reputation for a new publisher Low Sign from the first beta; signing reputation builds up over time

Assumptions in this plan

  • That CEF's windowless (OSR) mode only works with Alloy-style browsers. This comes from CEF's runtime split and needs confirming in Phase 1.
  • Pinning RNW 0.81 to match RN 0.81, rather than upgrading both first. Upgrading RN on Mac is a separate decision.
  • The Windows app having the same features as the Mac app, minus the out-of-scope list above. No Windows-only features are planned.
