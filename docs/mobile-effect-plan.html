Effect across Bay mobile

Move the mobile app’s asynchronous work onto one Effect runtime in a single migration: saving state, the content blocker, page scripts, site icons, snapshots, saved logins, links from other apps and clearing data. Keep the tab model, the render path and the native engine contract as they are.

This is the mobile counterpart of the desktop Effect plan, which left mobile out on purpose. It uses the same runtime shape, command boundary and failure vocabulary, so code reads the same in both apps. The work packages are dependency steps within one migration. It is complete when every row marked Migrate or Scope / adapt is done, the code it replaces is gone, and every gate passes on iOS and Android.

Plan only: no application code or dependency changes in this commit. Every decision below is resolved with the recommended answer.

1. What “properly implemented” means

One mobile service architecture shaped like desktop’s. Effect owns background jobs, file and network I/O, page work tied to a document, cancellation, bounded retries and failure reporting. It is not a second store, and it doesn’t reach into Swift, Kotlin or the coming Chromium embedder.

A runtime added beside the old timers and Promise chains doesn’t count. Each package removes what it replaces before the next one starts.

  • Covers startup, browsing-state persistence, language, lifecycle, the content blocker, page scripts and reading tools, snapshots, site icons, saved logins, page requests, the private session, incoming links, the link resolver, downloads, clear data and diagnostics.
  • Gives every timer, listener and background job one owner, one stop condition and one failure policy. UI timers and the navigation hot path stay plain.
  • Preserves every saved file and key (browser.json v2, locale.json, filter-lists/, bay-saved-logins, snapshots, tab states), private-tab rules, native event order, typing responsiveness and cold launch time.
  • Leaves out native engine code, the share and widget extensions, the Android Chromium embedder (PR #21), parked translation, mobile sync, and the desktop and CLI runtimes.
  • Ships on both platforms together: every package passes on iOS and Android before the next one.

Audit method: all 103 non-string TypeScript modules in apps/mobile/src (about 12,500 lines), the engine’s JavaScript API, 13 Node test files and 17 Argent e2e tests, at bc78a6ed (PR #21’s head). Asynchronous code was found by searching for timers, Promise chains, fetch, abort controllers and native listeners, then read by hand. This audit doesn’t replace running the app.

3. Runtime and service boundaries

  1. Synchronous start stays first

    installCrashReports() runs before the first screen, the store starts with in-memory data, fonts and the splash behave as today. Nothing that draws the first frame waits on Effect.

  2. One runtime and a handful of ports

    Files, Http, SecureStore, Engine (page scripts, data, downloads, private session), Lifecycle, Links, BrowserState and Diagnostics. A port is written when a service needs it, not for every native function.

  3. Services own the work

    Persistence, LocaleService, BlockerService, Snapshots, Favicons, Logins, PrivateSession, IncomingLinks, LinkResolver and ClearData. They depend on ports and pure functions, never on React components.

  4. Commands and hooks are the edge

    UI handlers and native callbacks run programs through runCommand, useCommand or useScopedWork. Services compose other programs directly and never call the runtime themselves.

  5. State lands in the store at chosen points

    Results are dispatched into Zustand after their scope is still open, which replaces identity and generation checks. Rendering is unchanged.

Lifetimes

  • App scope: AppState, Linking, share and download listeners; store subscriptions for saving, pruning, icon cleanup and the private session; the blocker. Never closed by backgrounding.
  • Tab scope: a pending snapshot, a saved-login lookup for a page request. Closes when the tab closes or loads a new page.
  • Document scope: Reader, the picker and inspector, Markdown copy, auto-Reader, find. Keyed by tab, address and load count, as the reading tools are today.
  • Sheet scope: resolving a link’s destination, loading saved logins in Settings. Closing the sheet aborts the work.
  • One writer per resource: browser.json, locale.json, lists.json, the logins document, the blocker’s apply, and the private-session call. Bursts coalesce; nothing is queued without a bound.
  • Leaving the foreground: left, the save flush and each view’s saveState start synchronously in the callback. Finalizers are idempotent and never wait on the network.

5. Complete implementation sequence

Packages follow dependencies and risk. Each ends with its tests passing and the replaced code deleted. Following apps/mobile/AGENTS.md, check each change with pnpm typecheck and pnpm test, run the e2e tests a package touches on both devices, and run the whole suite once at the end.

01Baseline, dependency and runtime

Owner: runtime infrastructure · prerequisite for every package

  • Record the baseline at the branch point: pnpm typecheck, pnpm test, root lint and slop, the full e2e suite on iOS and Android, the Hermes bundle size of expo export for both platforms, and cold launch on Release builds.
  • Add effect@4.1.3 exactly. Confirm Metro resolves a single copy and Hermes compiles the Release bundle on both platforms.
  • Write runtime.ts, commands.ts (runCommand, runCommandResult, Exit-aware: cancelled stays silent, failures report once), errors.ts (NativeUnavailable, Cancelled, shared Operation), react.ts and testing.ts (fake ports, test clock, a count of what services still hold).
  • Write the ports services need first: Files, Http, Lifecycle, BrowserState, Diagnostics. Diagnostics feeds the crash-report ring.
  • A development-only self-check runs once after the runtime builds: a layer, a finalizer, a typed failure and an interrupted sleep. A failure lands under Report a problem, so a Hermes incompatibility shows on device, not only in Node.

Exit: Type checks, lint, anti-slop and tests pass; both dev clients start with the self-check clean; Release bundles compile; a test runtime disposes to zero held resources.

6. Failure, retry and cancellation policies

Domain errors keep their current messages. Expected refusals, failures, interruptions and programming defects stay distinguishable. Tolerated failures stay quiet rather than becoming new alerts.

Operation Policy to implement
Expected outcomes A cancelled program, a closed sheet, a replaced document and a dismissed prompt are not errors: no toast, no crash report. Expected failures keep their current messages (notice.pageChanged, linkMenu.unreachable, settings.clearDataFailed).
Filter lists No retry within a run: a failing list keeps its cached copy and is tried again on the next launch or preference change, as today. HEAD times out after 10 s; downloads have no timeout (7 MB on a slow link is normal) but are interrupted when blocking is turned off.
Link destination 10 s for the whole resolution, no retry, aborted when the menu closes. The hop-by-hop fallback for ATS stays.
Page scripts Keep the 10 s timeout. No retry: the next navigation event runs the script again where that matters (hidden elements, tweaks).
Site icons and snapshots Best effort, once per host per launch and once per visit. Failures are dropped quietly; a programming defect is reported.
Persistence A failed write is reported once and the data stays dirty; the next change or leaving the foreground writes again. No retry loop and no backoff timer.
Logins and clear data Never retried automatically. A failed secure-store write is reported; a failed clear shows the Settings message.
User prompts Face ID, microphone, notifications and voice search are never retried or re-asked by a service.
Defects Any unexpected failure in a background service is reported once through Diagnostics into the crash-report ring; the service keeps serving the next job.
