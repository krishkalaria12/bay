Bay's desktop app on GPUI

Rewrite Bay's desktop window in Rust on GPUI, macOS first. The page stays Chromium's (and WebKit's for protected video). Everything Bay draws around it moves from React Native macOS to GPUI, and the app's logic moves from TypeScript stores into Rust crates beside the shared desktop core. Windows and Linux follow once macOS ships, replacing the WebUI host there.

Drafted 28 Nov 2026 against main at 6787688f0, which holds the shared desktop core (#35), engine choice (#36) and the browser gaps (#38). Work happens on refactor/gpui-port; Progress says what is built. It replaces the "one host for all three" question in Phase 6 of the shared desktop core plan: the single host becomes GPUI rather than WebUI. A reference port shaped it: a draft GPUI rewrite of a sibling Chromium browser's React Native macOS app, opened 27 Nov 2026, whose own source is Apache-2.0. Line counts are tracked files without tests or vendored code, rounded.

Known gaps

  • Settings and downloads are kept as written JSON until each has a typed home; Library, Boosts and the other documents aren't read yet.
  • bay_state::store leaves out, for now: Find; peeks; placing tabs into a pinned folder; the local files' order (normalizeLocalFiles). It takes addresses already resolved by a function it's given: the input rules (@bay/core resolveInput) have a Rust port in the mobile core (packages/mobile-core/crates/bay-core/src/input) to share rather than copy.
  • One change from the TypeScript store: a tab reopened into another space (its own has gone) is that space's. The TypeScript store kept the closed tab's space on it, which left the tab in no list that shows it.
  • The spike links the engine built on 20 Nov (~/chromium-build); engine/ has changed since and has no published prebuilt.
  • Argent can't drive the spike: it sees a Chromium browser and offers only its pages. Interaction checks need a person, or a tool that posts events to the app's process.
  • A covered window's page reads as hidden and draws nothing (Chromium's occlusion, as in Chrome). Screenshots of a covered window need --disable-features=MacWebContentsOcclusion.
  • Builds in packages/rust need rustup's toolchain first on PATH: a system Rust (Homebrew's 1.99) ignores rust-toolchain.toml. rust.sh and build-app.sh put it first.
  • GPUI turns on serde_json's preserve_order, so in the GPUI app (and workspace-wide test runs) the shared crates' JSON replies keep insertion order. Readers must not depend on key order; two tests that did now compare values.
  • bay-engine and bay-app run no tests yet: their test binaries would link Chrome's framework, which loads only from inside an app bundle. Phase 1 tests run on the stand-in engine.
  • The spike's input hooks are simpler than the reference port's: installed once per window class, never removed. Its menu holds Quit and Edit only.

1. Why GPUI, and what is proven

A browser's window has one hard requirement a general UI kit doesn't: Chromium's page is a native view, and Bay draws over it (command bar, Peek, menus, popovers, drag previews). Stock GPUI has no way to place a native view inside its window. The reference port added one, and that is most of why this plan starts from it.

What the reference port shows works on macOS

  • The page under GPUI. A native view element in GPUI places the page's view beneath GPUI's Metal layer and erases GPUI's drawing over it. Anything painted later lands on top of the page, in the same window. The view follows GPUI's clip, rounded corners, scale and opacity.
  • Chromium owns the window and the run loop. GPUI attaches to a window the engine created ("hosted" windows) and routes sendEvent:, keyDown:, makeFirstResponder: and performKeyEquivalent: between GPUI and the page.
  • Long lists. One virtual list helper for every list; the sidebar's frame cost stays flat from 100 to 800 tabs.
  • The rest of a browser. Sidebar, tab strip, split view, Peek, a small-window mode, settings, native menus, onboarding, sync, media, fullscreen, picture in picture, plugins and AppleScript, on a Rust state crate with a stand-in engine for tests.
  • GPUI fixes a browser needs. Swipe latency, frame and input-latency hooks, render to image, text input, Liquid Glass and system materials.

What it doesn't show

  • Screen readers. It has almost no accessibility code: a few labels on native views, no AccessKit tree for GPUI's own UI.
  • Typing in other languages and dictation, automatic picture in picture and the real fullscreen transition: listed as unchecked.
  • Windows and Linux. Its GPUI patch adds no native views there; the Windows and Linux engine backends are thin stubs. Bay would be first there.
  • Its own review. It is a one-day draft written by parallel workers; its merge check, audits and review rounds hadn't run when it was read.

The fork is the cost. The patch touches 88 files of GPUI, including the macOS window, display link and text system. Every move to a newer GPUI is a merge into that. GPUI itself says it is pre-1.0 with frequent breaking changes and is tied to Zed's needs.

5. Phases

Phases run in order. Phase 0 is a gate: if it fails, the plan stops and the findings go in Known gaps. Phase 6 waits for Phase 5. Within Phase 3 the batches are independent.

Phase 0 · Spike and gate

gate

One GPUI window on macOS that hosts a real Bay page, with enough UI to answer the hard questions. Throwaway UI, kept crates.

  1. Vendor GPUI with the patch under packages/rust/third_party/gpui; build on the pinned toolchain; record the upstream commit.
  2. bay-engine minimal: start NNCore, open one window, show one tab's view through GPUI's native view element.
  3. A sidebar of 500 rows on the virtual list, a command bar drawn over the page, a text field in it.
  4. Run every check below on a copied BAY_DATA_DIR.
Go if
All pass: the page resizes with the window without tearing; the command bar draws over the page and takes clicks and keys; Japanese and Chinese input work in the bar and in the page; VoiceOver reads and activates a sidebar row; two-finger swipe moves between spaces; the 500-row sidebar scrolls within the 8.3 ms budget; Chromium's context menus, extension popups and DevTools still show; sign-ins survive (same Safe Storage keychain name); the window backdrop and grain draw behind the sidebar.
Stop if
Any of the page, input or VoiceOver checks can't pass without rewriting the patch's native view design.

Phase 1 · Foundations

  • Engine ABI. NNCore exports bay_engine_api: version, size, event sink, host calls (window and tab verbs) and engine calls (services). Verbs follow the calls the TS bridge makes today, so each one maps across. A stand-in engine implements the same trait for tests.
  • State. bay-state ports the stores and the coordinator's commands. Persistence reads and writes today's documents in place (D6). Port the store, runtime and lib tests first; they are the spec.
  • Primitives. Tokens and themes from lib/theme.ts, virtual list, text input, native menus, SF Symbols, glass.
  • Tooling. Toolchain pin, clippy lints, fast pattern checks, scripts/gpui/build-app.sh producing a signed Bay.app with NNCore and its helpers, a pnpm gpui dev run, and the dev-eval harness.
  • Services. Swift services linked through C functions from bay-mac/build.rs, starting with Keychain and Sparkle.
  • Windows and Linux CI runs cargo check on the new crates, so nothing macOS-only leaks into the shared ones.

Phase 2 · The window

The daily loop, at parity with the React Native app: what someone uses in the first minute.

  • Window chrome, traffic lights, fullscreen, multiple windows, window restore.
  • Sidebar: favorites tiles with unread counts, pinned tabs and folders, today's tabs, either side, auto-hide, top tab bar mode, drag and drop, sidebar undo, keyboard focus (⌘.).
  • Spaces: icons, themes, profiles, swipe between spaces.
  • Tab lifecycle: open, close, sleep, put away, restore; Bay's archive rules.
  • Command bar (⌘L, ⌘T), address field, suggestions, ⇧↩.
  • Split View, Peek, Find, keyboard shortcuts, app menus.

9. What doesn't change

  • The engine: Chromium patches, NNCore internals, the WebKit engine. NNCore only gains an exported ABI.
  • The phones: SwiftUI and Compose on packages/mobile-core.
  • The shared desktop crates already in packages/rust; the GPUI app links them as Rust libraries instead of through the pod.

  • Release rules in AGENTS.md: LZMA DMGs, symbol stripping on the private copy, signed-candidate and Sparkle checks.

10. Decisions

Each has a recommendation. Taking all of them as written is a coherent plan; changing one may change others, noted where it does.

D2 Which GPUI? decided 28 Nov 2026

Options were: (a) vendor the reference port's GPUI snapshot and its patch; (b) upstream GPUI, with Bay writing its own native view element; (c) the snapshot gpui-kit pins.

(a). The native view element, hosted windows and input routing are the hardest part of this plan, and they exist and are Apache-2.0. Taken whole into packages/rust/third_party/gpui (Zed a3ce8d5e8 plus the patch, kept beside it as bay-base.patch), credited in NOTICE, and owned from then on: no syncing with the reference port. Upstream merges go on a schedule.

D3 Component kit open

Options: Bay's own primitives, or depend on gpui-kit (75+ components, used in production on desktop).

Recommend Bay's own primitives. gpui-kit builds on its own GPUI snapshot, and one app can't have two GPUIs. Bay's UI is custom throughout, so a kit's look would be restyled anyway. Copy a gpui-kit piece (both are Apache-2.0) when one saves real work, adapted to Bay's GPUI.

D4 Engine boundary decided 28 Nov 2026

Options were: (a) Rust calls NNCore's Objective-C API through a .mm bridge; (b) NNCore exports a versioned C ABI (JSON verbs, an event sink) and Rust calls that, with a small .mm only for views and window hooks.

(b). The same ABI can come from the Windows and Linux engine in Phase 6, so bay-engine is written once. JSON verbs match what the TS bridge sends today, which makes each call a mechanical port and lets the stand-in engine replay real traffic. Hot paths (tab views, frames, input) stay native. It grows from what NNCore already exports: nncore_engine_call and its event sink (nncore_engine.h, ABI version 1) for profile services; window and tab verbs join it.

Phase 0 runs on (a) for the view hosting: bay-engine compiles the current host glue (packages/chromium/ios/*.mm), so the spike keeps today's data folder, keychain item and content blocker. Phase 1 moves the app onto (b).

D5 App logic open

Options: rewrite the stores and coordinator in Rust, or keep the TS logic in a JavaScript runtime (Hermes) that drives GPUI.

Recommend Rust. Two runtimes in one app is the cost this move removes. GPUI's model (entities, notify) is a natural home for the stores. Port the 213 test files' store, runtime and lib cases first; they pin the behaviour.

D6 User data open

Options: read and write today's documents in place, or migrate once to a new format.

Recommend in place. Same data folder, same document names, same schema versions. Fixtures written by today's app are read by bay-state tests, and the reverse. Anyone can go back to the React Native build during the rollout without losing anything.

D7 Swift modules open

Options: keep the Swift code behind C functions, or rewrite it in Rust with objc2.

Recommend keeping Swift where it wraps Apple frameworks: Sparkle, Keychain, Calendar, Handoff, Translation, Apple Intelligence (Tidy), capture, WebKit. Remove the React Native module layer. Write the thin window and menu glue in Rust. Move pure logic (import, sync) to the shared Rust crates (bay-import, bay-sync).

D8 Where the code lives open

Options: the packages/rust workspace; a new workspace at the repo root; a new apps/desktop workspace.

Recommend packages/rust. It is the desktop workspace already. A root workspace would move packages/adblock/target and clash with packages/mobile-core's own workspace. The new crates are ordinary libraries beside the bay-desktop static library, which keeps serving the React Native app until Phase 5.

D9 Branch and PR decided 28 Nov 2026

refactor/gpui-port, branched from main at 6787688f0 (which holds #35, #36 and #38), in the sibling worktree bay-gpui. One PR, commits in validated chunks, pushed often. Bring in main by merging, not rebasing. The GPUI app is a separate target, so nothing on main changes for users until Phase 5.

D10 Look open

Options: match today's UI, or redesign during the port.

Recommend matching first. Screenshot comparisons against the React Native build make parity checkable. A redesign during the port hides regressions. Change the look after the switch.

D11 Work on the old app meanwhile open

Options: no freeze; fixes only from Phase 3; a full freeze now.

Recommend fixes only from Phase 3. Until then the React Native app moves on as usual and its changes become parity rows. From Phase 3, new desktop features go into the GPUI app (and into the WebUI host only if Windows or Linux needs them before Phase 6).

Engine choice (#36) and the browser gaps (#38) are on main, so their features are parity rows too.

D12 Tests open

Options: port the acceptance suite, write new Rust UI tests, or both.

Recommend both. gpui::test UI tests on the stand-in engine for every screen (fast, run in CI), and acceptance runs on the real app driven as a Mac app, porting the existing scenarios. Debug builds get a strict mode that fails on blocking work in render paths.

D13 Rollout open

Options: nightly feed first; a separate side-by-side app; a hard switch.

Recommend nightly first. Same bundle ID, data folder and keychain names, so it is an update, not a second app. A side-by-side app risks two processes writing one profile, or a copied profile that loses passkeys. Stable switches after a clean nightly cycle (Phase 5).

D14 Oldest macOS open

Recommend keeping macOS 14.0. Liquid Glass (macOS 26) where available, today's backdrop and grain below it. Raising the floor would drop current users for no gain in this plan.

D15 Windows and Linux timing open

Options: after macOS ships; in parallel from Phase 2.

Recommend after macOS ships, with cargo check of the shared crates on Windows and Linux from Phase 1. The native view element doesn't exist there, and the WebUI host already works. The Phase 6 spike can start earlier if someone has Windows or Linux time free.

D16 Icons open

Today <Symbol name="…"> is a native view that draws Apple's SF Symbols on macOS (weights, sizes, two places use hierarchical colour). Windows and Linux draw Lucide paths under the same names, generated by packages/desktop/scripts/lucide-symbols.mjs into lucideSymbols.web.ts (288 names). Options: (a) bundled SVGs on every platform, Lucide's included; (b) SF Symbols from the system on macOS, bundled SVGs elsewhere.

Recommend (b). One Icon in bay-widgets, keyed by today's names, so each call site ports as is. On macOS it asks the system for the symbol at the size, weight and scale it needs, keeps the result as an alpha mask in a cache, and GPUI tints it; the reference port draws its symbols this way. On Windows and Linux the generator writes Lucide's SVGs (ISC, credited in NOTICE) into the crate's assets, drawn with GPUI's svg(). Glyphs Bay draws itself (caption buttons, badges) are SVGs on all three.

Copying SF Symbols out as SVG files isn't an option: Apple's licence lets an app use them through the system, not ship them. (a) would also change the Mac's look (D10), and the icon picker saves SF Symbol names for spaces and folders, so macOS needs the system symbols regardless.
