Bay for iPhone.
A quiet browser with a glass bottom bar.

Build Bay's mobile browser in apps/mobile with Expo, HeroUI Native and Expo UI. The interface follows the Lens demo you shared: it opens to a search field, the page runs edge to edge, and one floating glass bar holds the controls. Agents check every screen in the iOS simulator through Argent.

Phase 0 (the project and agent tooling) is done and runs on the simulator. Everything after that is a plan; no browser feature is built yet. iPhone comes first, then iPad, then Android.

Decisions

Accepted

Decision Why
Expo SDK 58 (React Native 0.88, React 19.3), Expo Router, dev-client builds Your choice. Expo UI and our own native modules need a native build, so Expo Go is out.
HeroUI Native 1.0 with Uniwind (Tailwind 4) for React-rendered UI Your choice. The official create-heroui-native-app template wires up Uniwind, providers and peer dependency versions.
@expo/ui/swift-ui for the controls that float over the page Your choice. Liquid Glass (glassEffect, buttonStyle("glass"), GlassEffectContainer) and native menus, popovers and context menus only feel right in SwiftUI.
Split rule: Expo UI for anything drawn over web content (bars, search, menus, popovers). HeroUI for full screens and sheets with React content (settings, archive, inspector panels, the Fonts list). Keeps each library where it's strongest and avoids two looks for the same kind of control.
apps/mobile is a standalone project with its own pnpm-workspace.yaml and lockfile, excluded from the root workspace The root hoists react-native-macos 0.81 for the desktop app, and mobile needs React Native 0.88. This follows the pattern already used by apps/web, apps/cli and apps/videos.
Bundle id in.krishkalaria.bay.mobile, URL scheme bay:// Sits next to the desktop id in.krishkalaria.bay.
The repo's oxlint and oxfmt, not the template's ESLint and Prettier One lint and format setup across the repo; apps/mobile passes both.

Proposed (confirm before phase 1)

  • Our own web view module (apps/mobile/modules/bay-webkit) instead of react-native-webview. See the next section.
  • iOS 26 minimum, which Liquid Glass needs (Lens sets the same floor). The simulators here run iOS 27.
  • zustand for browser state, as on desktop (apps/browser uses zustand 5), and expo-sqlite for history, tabs and per-site rules.
  • Reuse @bay/core through "@bay/core": "file:../../packages/core", as apps/web does: omnibox, bangs, engines, suggest, calculator, cleanUrl, fuzzy, siteSearch, textFragment.

The web view engine

Every iOS browser must render with WebKit. Apple's BrowserEngineKit exception covers only the EU and isn't worth the cost here. So the real choice is how much of WKWebView we can reach. Most of the target UI depends on WebKit features that react-native-webview doesn't expose.

Needed for WebKit API react-native-webview 14 Own Expo module
Ad, tracker and cookie-banner blocking WKContentRuleListStore No Yes
Tab cards takeSnapshot(with:) No Yes
Bar that hides on scroll, pull gestures scrollView delegate, native on the UI thread Throttled JS events Yes, can drive Reanimated values directly
Link menu with preview and custom actions contextMenuConfigurationFor Limited Yes
Private tabs WKWebsiteDataStore.nonPersistent(), separate store per profile Incognito flag only Yes
Reader, hide elements, inspector, fonts WKUserScript in a separate WKContentWorld Page world only Yes, page scripts can't see or tamper with ours
Find on page, downloads, media UIFindInteraction, WKDownload, media playback APIs Partial Yes
Many tabs without a reload storm We decide which web views stay live and which become snapshots One view per component Yes

Recommendation: build bay-webkit as a local Expo module (npx create-expo-module --local). Define the TypeScript interface first: a native view plus TabEngine functions for load, back/forward, snapshot, scripts, rule lists and events. Implement iOS with WKWebView, and later Android with android.webkit.WebView behind the same interface. The repo already ships five Expo native modules for macOS (sync, shell, nncore, shaders, import), so the pattern is familiar.

Architecture

Routes · src/app

One browser route (start page, page view, tab switcher and search as overlays of the same screen, so the web view never remounts). Settings, archive and site settings are Expo Router sheets.

Chrome · src/chrome

Expo UI Host trees: bottom bar, search card, popovers, edit-mode toolbars. One GlassEffectContainer so glass shapes morph into each other.

Panels · src/panels

HeroUI Native screens and sheets: settings, archive, reader settings list, inspector details, fonts, downloads.

State · src/store

zustand stores for tabs, the current tab and the omnibox, persisted to expo-sqlite (history full-text search, tab restore, per-site rules). The tab model matches desktop's where it can, so sync is a mapping rather than a rewrite.

Shared logic · @bay/core

The omnibox pipeline already used on desktop: suggestions, bangs, engines, calculator and currency, URL cleaning, site search.

Engine · modules/bay-webkit

Swift: WKWebView pool, content rule lists, user scripts in an isolated world, snapshots, scroll and navigation events, context menus, downloads.

Sync · @bay/sync (phase 5)

The desktop's end-to-end-encrypted folder sync, through iCloud Drive. Its BaySync Swift module already targets "apple". Only the folder picker (AppKit) needs an iOS version.

Browsing core

A browser you can use every day, with no extras yet.

  • bay-webkit: view, navigation, title, URL and progress events, scroll offset, snapshot, context menu, new-window handling.
  • Start page with wallpaper and the three-button glass bar.
  • Search card: address field, pinned sites, history and suggestions from @bay/core, inline autocomplete, the ↖ fill button.
  • Page view: edge-to-edge web view, floating bar that hides on scroll, back and forward edge swipes, pull to reload.

  • Link menu: new tab, background tab, copy, share, and where it goes.
  • Settings: search engine (DuckDuckGo, Brave, Kagi, Ecosia, Google, Bing, using desktop's engine list), clear data.

How agents build and check each screen

  1. Read apps/mobile/AGENTS.md, export DEVELOPER_DIR, and run pnpm ios once per native change and Metro in the background.
  2. Use Argent to launch in.krishkalaria.bay.mobile. Take tap targets from debugger-component-tree for React content and from describe for native or SwiftUI controls, never from screenshot pixels.
  3. Screenshot the result and compare it with the matching frame in .reference/. Use screenshot-diff against our own previous baseline to catch regressions.
  4. Record each finished flow once as an Argent e2e test (argent-create-e2e / argent-qa-e2e), then replay it as a smoke test before every commit.
  5. For any performance claim, profile with react-profiler-* for JS and native-profiler-* for scrolling and web view work.

Lens itself can't be installed on a simulator: it's App Store and TestFlight only, the simulator has no App Store, and App Store builds are encrypted device binaries. To compare against the real app, install Lens on an iPhone connected by cable and drive it with Argent's argent-ios-device-* skills.

Risks

Risk Mitigation
Expo UI's SwiftUI API changes between SDK versions (for example, native tabs props changed in SDK 55). Pin Expo minor versions. Keep all @expo/ui use inside src/chrome so an upgrade touches one folder.
Each list in WKContentRuleList has a rule limit (about 150,000), and compiling large lists is slow. Split lists by category, compile off the main thread, cache compiled lists, and measure compile time on a real device.
Apple Pay is unavailable in web views that inject user scripts. Check on a device in phase 5. If needed, skip injection for payment pages or inject on demand only.
Default-browser and passkey support depend on Apple granting the web-browser entitlement. Apply early, in phase 2, so approval is in place by phase 5.
Mixing HeroUI and SwiftUI could make two different-looking apps. Follow the split rule above and pull shared colours and type into Uniwind tokens that both sides use.
Following Lens too closely. Match layout and interactions. Bay's name, icon, wallpaper art, colours and copy stay Bay's own.
Machine setup: xcode-select points at the Command Line Tools, and Metro started with CI=1 doesn't watch files. Both are documented in apps/mobile/AGENTS.md.

Open questions

  1. Do you approve the custom bay-webkit module over react-native-webview? It's the biggest decision in phase 1.
  2. Is iOS 26 the minimum, and is iPad in or out of the first release?
  3. Should the search card's text field be a native SwiftUI TextField (best glass and keyboard behaviour) or a HeroUI SearchField inside a glass container (easier styling)? A short spike in phase 1 settles it.
  4. Should desktop sync land before the first TestFlight build, or after?
  5. Local signing (like desktop releases) or EAS Build for TestFlight?
  6. When should Android start: after the iOS 1.0, or alongside it from phase 3?
