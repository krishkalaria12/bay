Plan · 10 November 2026 · one document for the mobile app

Bay for iPhone and Android.
One Lens design, WebKit on iOS, Chromium on Android.

Build Bay's mobile browser in apps/mobile with Expo and HeroUI Native. Both platforms get the same design, the Lens demo you shared: it opens to a search field, the page runs edge to edge, and floating controls sit at the bottom. iOS draws it in Liquid Glass. Android draws it with our own components, the way Arc Search does on Android: no Material and no imitation glass.

This is the whole mobile plan in one place: how the app is built and tested, what is still missing, what the next round adds, and the order the work happens in. It merges three earlier documents — the roadmap, the 5 November iOS parity audit and the next round's plan — so there is one plan and one set of item ids (I, A, B) to point at.

01 · Design

One design, drawn natively on each platform

  iOS Android
Design Lens, on both: same screens, layout, flows and gestures (the screen list is under Target UI)
Floating controls Liquid Glass through @expo/ui/swift-ui (buttonStyle("glass"), glassEffect, GlassEffectContainer) Our own React Native views, following Arc Search for Android: flat surfaces, translucent fills and hairline edges; over a page, the bar takes the page's colour. No Material components, ripples or elevation, and no blur pretending to be glass.
Sheets and screens HeroUI Native, shared (settings, archive, reader settings, inspector panels, fonts, downloads)
Icons SF Symbols Material Symbols outline paths (src/chrome/MaterialSymbol.tsx), the same style Arc uses on Android
Motion and gestures Reanimated and Gesture Handler, shared: the bar hides on scroll, swipe the bar to switch tabs, drag up to expand it

Arc's Android app shows the pattern: a flat bar with a tab-stack button, a wide translucent pill in the middle, and a control that pulls up into a tinted sheet with back/forward, the domain, copy link, reload, a row of tiles (Translate, Pinned, Find, Share), and a blocked-trackers line. We use that way of drawing for Lens's layout. The placeholder already does: StartToolbar.ios.tsx uses glass buttons, and StartToolbar.android.tsx uses flat round buttons in the same places.

02 · Testing

Testing: iOS completely, Android for every UI change

  • iOS is tested completely: every flow, screen and state, with Argent on the simulator.
  • Every UI change is also tested on Android before it's done: run it on the emulator, screenshot it next to iOS, and pass pnpm e2e on both. The Android UI is our own code, so it breaks independently; passing on iOS is never enough on its own.
  • Each finished flow is recorded once as an Argent e2e test with a launch map (ios: / android:), so one file runs on both.
  • Engine work adds a parity check: the same page gives the same features and blocking results on both engines.
  • Performance claims need Argent's profilers on both: native-profiler-* uses Instruments on iOS and Perfetto on Android.
Command (in apps/mobile) What it does
pnpm start Metro, serving both apps (run it in the background).
pnpm native Boots the iOS simulator and the bay-pixel emulator, then builds and installs both dev clients in parallel. pnpm ios or pnpm android builds one.
pnpm e2e Boots both devices if needed and runs every Argent test in .argent/e2e on iOS, then on Android.
03 · Engines

Two engines, one API

The app's JavaScript talks to one interface, @bay/engine (the local Expo module modules/bay-engine). Every feature ships on both, built with each engine's own tools. Page scripts (reader, hide elements, inspector, font identifier) are shared JavaScript injected into an isolated world on both engines.

04 · Architecture

Architecture

Routes · src/app

One browser route: the start page, page view, tab switcher and search are overlays of one screen, so the engine view never remounts. Settings and archive are sheets.

Chrome · src/chrome

Floating controls, search card, popovers, edit-mode toolbars: *.ios.tsx in SwiftUI glass, *.android.tsx as our own views. Each pair shares one props type.

Panels · src/panels

HeroUI Native screens and sheets, the same on both.

State · src/store

One zustand store for tabs, history, pins, the archive and preferences, saved as a versioned JSON file (expo-file-system, written atomically). The tab model matches desktop's so sync is a mapping.

Engine API · modules/bay-engine

EngineView, Tab (load, back and forward, snapshot, run script in an isolated world, find), profiles, blocking, downloads and events. ios/ wraps WKWebView; android/ wraps the system WebView, then bay-engine.aar.

Page scripts · modules/bay-engine/scripts

Shared JavaScript injected on both engines: reader, hide elements, inspector, font identifier.

Android embedder · engine/mobile → //bay/mobile (phase 7)

C++ on content/public, with //bay/content for blocking; copied into the Chromium tree by an apply.sh, like engine/nncore.

The one new shared piece: Page requests

Four separate gaps are the same shape: a page asks a question and waits for the person to answer. They are alert/confirm/prompt (I3), location, camera and microphone (B7), HTTP sign-in (B3), and "open this in another app?" (B5). Build one engine event, onPageRequest, one call, answerPageRequest(id, answer), and one shared sheet. Each native side only holds the completion handler until the answer arrives. It also keeps the promise of one design with no Material on Android, and each site's answers can feed per-site settings (B12) later.

Found on the real phone, which reading the code couldn't show

  • Every Android download sat at "pending": DownloadManager runs as a JobScheduler job, and the system holds those jobs back while the phone is warm (thermal status "moderate", common while charging on mobile data).
  • On Android 13 and later Bay showed no notifications at all, the I1 media notification included, because it never asked for POST_NOTIFICATIONS.
  • URLUtil.guessFileName saved a film as "www.bin". Names now come from Content-Disposition or the address.

Still unverified: none of #11's Swift has been compiled. It only passed swiftc -parse, and the iOS 26 BGContinuedProcessingTask calls are the riskiest part. pnpm e2e wasn't run for either PR. Stage 0 now starts with an iOS build.

16 · Risks

Risks

Risk Response
Risk Mitigation
Testing mostly on iOS lets Android UI bugs through: Android's controls are our own code. Every UI change is checked on the emulator, with screenshots next to iOS, and pnpm e2e must pass on both.
Swapping Android's engine late (phase 7) could break features built on the system WebView. Keep everything behind @bay/engine; e2e tests use only the UI, so the same tests prove the swap.
The system WebView lacks some features (no content-blocking API, limited profile control). Interim versions (request interception, a separate profile) until our Chromium takes over in phase 7.
Android engine builds need Linux and about 100 GB of disk. Build on the Linux machine and publish the AAR; the app only downloads it.
No stable Chromium embedding API since WebLayer was deprecated; content/public changes every release. Keep //bay/mobile small; rebase it with desktop's Chromium updates.
Shipping Chromium makes the Android app much larger than one using the system WebView. Measure in phase 7; App Bundles split by ABI; strip symbols as desktop releases do.
Custom Android controls take more work than stock components and can feel off. Follow Arc's Android app closely for touch targets, spacing and motion; build shared primitives (round button, pill, sheet) once.
iOS content rule lists have a per-list rule limit (about 150,000); WebKit disables Apple Pay in pages with injected scripts. Split lists by category and cache compiled lists; skip injection on payment pages if needed.
Machine setup: xcode-select points at the Command Line Tools; Metro with CI=1 doesn't watch files; cold emulator boots can show a System UI dialog. The scripts set the toolchain paths and close system dialogs after boot; the quirks are in AGENTS.md.
Risk Response
This audit comes from reading code, so some gaps may behave differently when run. Stage 0 runs first and corrects this file.
Real new windows (B19) are the hardest item: WebKit needs a view returned synchronously, while React mounts tabs itself. Do it last in stage 2. If it blocks, fall back to opening a new tab without an opener and list the sign-ins that fail.
Google may still block sign-in with a normal user agent. Both apps now send one (B1), and neither has been tested signing in. If Google still refuses, the remaining signs of a web view are on Android, and our Chromium removes them later.
#11's iOS code has never been compiled, and BGContinuedProcessingTask is new in iOS 26. Build it before anything else in stage 0. Without the plugin's BGTaskSchedulerPermittedIdentifiers entry, Bay skips the task rather than crash, so an old prebuild falls back to background time.
Our Now Playing info may conflict with WebKit's own. Test on a real iPhone before writing any code (I1).
New work on the system WebView gets replaced in phase 7. Stay behind @bay/engine and let e2e tests prove the swap.
Store timing. I recall Google Play requiring newer personal accounts to run a 14-day closed test with 12 testers first. I didn't verify this. Check the account type now. If it applies, the closed test has to start by about 1 December.
I don't know the format of Arc's tab export. Export a real list before 23 November and use it as the test file. The parser should find links in any text.
