Effect across Bay desktop

Move desktop asynchronous orchestration to Effect in one complete implementation. Keep the synchronous browser interaction paths and shared native contracts intact.

This is the implementation plan requested after the repository audit. The work packages below are dependency steps within one migration. Completion means every workflow marked Migrate or Scope / adapt is handled, its previous orchestration is removed, and the complete validation gate passes.

Plan only. No application code or dependency has been changed. Architecture choices below are recommended decisions, adopted for this plan. Compatibility and performance remain proof obligations.

1. What “properly implemented” means

One coherent desktop service architecture. Effect owns long-running jobs, I/O coordination, scoped resources, cancellation, bounded retries and background failure handling. It does not become a second UI store or a new native engine.

All in-scope work lands before the migration is considered complete. Internal reviewable commits are useful; a small wrapper released while most orchestration remains ad hoc does not satisfy this plan.

  • Cover startup/persistence, encrypted sync, imports, live folders/accounts/calendar, search/previews/translation, capture/Library/sharing/downloads/files, automation/extensions/system workflows and diagnostics.
  • Give every background task, timer and native subscription in those workflows an owner, a stop condition and a failure policy. Preserve deliberately synchronous and UI-local work.
  • Keep mobile, the website, videos and the standalone Bun CLI outside this migration. Their shared package interfaces remain usable without importing Effect.
  • Preserve saved data, sync protocol, permissions, authentication, privacy behavior, undo, native event order and browser responsiveness.

Audit method: inventory scan of 489 non-test TypeScript/TSX/MJS modules across apps/browser/src and six relevant package source trees, followed by focused tracing of asynchronous workflows, package/native contracts and regression suites. Vendor and fixture directories were excluded from that census. The census is coverage context, not a claim of a line-by-line review or a runtime test pass.

3. Runtime and service boundaries

  1. Native contract guard and synchronous bootstrap

    Keep nativeApi.tsx compatibility checking and the import-first bridge batching hook. Install early error reporting, establish React batching, load/hydrate saved state synchronously, and preserve page-handoff-before-window-close behavior.

  2. One app runtime and a small set of infrastructure ports

    Build native, persistence, HTTP, scheduler and diagnostic services from already available capabilities. Establish readiness before mounting dependent roots or accepting background commands, without letting asynchronous layer acquisition interleave with the synchronous bootstrap prefix. Layer acquisition registers owned resources. Transient connectivity or denied permissions must not poison a memoized app layer; perform recoverable reads/connects as operations.

  3. Domain services with scoped work

    Sync/import, activity/calendar, page work, Library/downloads and automation/system workflows use typed programs. Scope jobs by stable resource identity. Services may depend on ports and plain domain functions, without importing React components or acquiring stores through circular module initialization.

  4. Explicit command and event boundaries

    Native callbacks and UI handlers run programs through a small command adapter. Domain programs compose other programs directly. Preserve typed outcomes and interruption with Exit-aware handling; only legacy callers that expect Promise rejection receive it.

  5. Ordinary state updates and synchronous browser actions

    Commit results to Zustand/React at deliberate points after rechecking identity/generation. Immediate tab activation, focus, native command IDs and batched page reports stay synchronous. Resource ownership does not require queueing every event.

The names above are proposed ownership, not a requirement to create a file for every exported method. Keep existing names where clearer. Ports cover workflows actually needed; do not mechanically wrap all native functions. Pure domain code cannot import the runtime. Raw shared packages cannot import desktop service implementations.

Store ports provide narrow read / subscribe / apply operations using plain snapshots. Production composition wires the existing Zustand stores; unit tests supply fake ports. No runtime import inside a store initializer and no service constructor that starts hidden network work.

Lifetime, concurrency and shutdown contract
  • App-owned scopes hold durable listeners, the scheduler and long-lived workers. Each worker handles a failed job and remains available for subsequent jobs; failure must not silently kill a refresh service or unrelated siblings. Closing one window cannot stop sync or another window’s work.
  • Window/document scopes interrupt previews, captures, translation and UI discovery on close or document replacement. Use document/navigation generations for document-bound work and a tab lifetime for work that survives view replacement. Moving a retained page transfers ownership without interrupting it; component unmount alone cannot dispose transferred tab work.
  • Profile/account jobs key caches, locks and generations by identity. Disconnect/delete increments a generation before removing state, preventing an old result from restoring it.
  • Keep one active sync cycle, one reconciler per automation domain, one publication operation per Easel, preserving immediate busy rejection, and one relevant mutation per resource. Native history already serializes writes per profile; reuse that guarantee.
  • Use coalescing triggers for “refresh/reconcile again”, bounded queues for real commands and bounded parallelism for independent reads. Native callback producers must not block waiting for a full queue. Critical events stay lossless or trigger explicit snapshot recovery; replaceable progress can coalesce.
  • Scope finalizers remove listeners, timers, watchers, temporary page state and tracked work exactly once. They are idempotent and cannot launch unbounded networking.
  • On willQuit, synchronously flush and freeze the correct session, then call replyToTerminate. Keep the runtime alive through quitCancelled. Runtime disposal is for confirmed teardown/test restart, not the cancelable quit request. Do not promise asynchronous finalizers will run after process termination.
  • Successful quit relies on already durable local state; network sync, telemetry and file uploads are never prerequisites to terminating. Async local writes have explicit durability tracking and do not weaken the existing synchronous final-save contract.

6. Failure, retry and cancellation policies

Use domain errors that preserve existing codes. Shared metadata can name operation, resource identity and sanitized native cause. Expected refusal, failure, interruption and programmer defects must remain distinguishable. Preserve intentional optional-enrichment fallbacks and partial success rather than turning every tolerated failure into a visible alert. “Cancelled” is not an error toast or a telemetry incident.

Operation Policy to implement
Recoverable read/network failure Preserve current documented retry behavior when present. For new safe-read recovery use at most two retries with jittered 500 ms / 1 s delays inside the operation’s timeout; abort interrupts fetch. No retry storm on wake or reconnect.
Rate limit, auth, permission Rate limits honor provider timing and schedule a later refresh. 401, SSO, denied permission and user cancellation do not auto-retry or repeat prompts. Manual reconnect is explicit. Token refresh is serialized and retried only where its existing protocol allows it.
Sync Keep the current normal-cycle/debounce behavior and stalled state. Retry only safe substeps at documented checkpoints. Never restart a full cycle blindly after a potentially committed write; preserve journal identity and native settlement.
Imports and protected writes No automatic retry of consumed vault tokens, credential/cookie imports, password writes, destructive clear-data, export authorization or user prompts. Dia retains its existing grace window/poll cap. Per-extension failures remain independently reportable.
Publication/rename/delete Persist required recovery state before mutation, preserve native/HTTP idempotency rules, and determine ambiguous outcomes by reading state. Interruption is not a rollback. Keep a lease until non-cancellable native work settles.
Partial fan-out failure Use independent outcomes where the product already preserves successful siblings, such as providers/extensions. Do not use fail-fast fan-out for these. Keep GitHub detail batches all-or-none to avoid false “item disappeared” changes.
Timeouts Preserve existing domain limits, including eight-second anonymous previews and sixty-second sharing requests. Introduce timeouts only where the underlying operation and recovery are known. Human permission/auth prompts are not governed by a generic network timeout.
Finalizer failure Best-effort cleanup logs locally through sanitized diagnostics. Durability failures remain explicit and dirty state is retained. Finalizers cannot wait indefinitely on networking or silently release an in-flight native mutation’s serialization guard.
Background defects Supervise and report once through the existing error boundary/consent-aware reporting path. Do not convert every defect to a normal success or restart a failing worker forever. Expected cancellation is silent. Redact credentials, recovery phrases, vault tokens, account identifiers, page content and sensitive URLs before serializing any error, span or log.

Use the version-matched retry guidance, scopes and runtime guidance. A runtime can run finalizers for registered resources when its scope closes; neither Effect nor JavaScript guarantees cleanup after an OS kill.
