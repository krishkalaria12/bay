Engine choice and feature gaps

Let people pick which engine their pages open in, per browser, per site and per tab. Then fill the gaps found in a feature sweep: local agents, questions about a page, custom filters, secure DNS, hooks, plugins and a few smaller items.

Drafted 24 Nov 2026 against main at 4be8f6715. Nothing here is built yet. Engine choice is macOS only, behind hasWebKit(); every other item says which platforms it covers.

1. Choose your engine P0

Every page opens in Chromium or WebKit. Today Bay picks the engine and there is nothing to set. This feature hands that choice to the person: one setting for the whole browser, rules for single sites, and a switch on any open tab. Bay's automatic behaviour stays the default, so nobody who ignores the setting notices a change.

This reverses a standing rule. On 5 Nov 2026 every engine choice was taken out: Bay decides, and Settings › Engines and Site Controls only explain. This plan brings the choice back on purpose. The automatic rules from that change become the Automatic mode below.

What Bay does today

  • store/engines.ts resolves a tab's engine: Bay's and Chrome's own pages stay in Chromium, a fixed list of streaming sites opens in WebKit, and everything else opens in Chromium.
  • lib/pageEngines.ts moves a page to WebKit when its protected video stalls in Chromium. It asks before a reload would lose unsaved work (PageWorkService.mayLeavePage) and handles Back across engines (goBackAcrossEngines).
  • A page's links stay in its engine, so cross-site sign-ins return signed in; a typed address goes to its own site's engine.
  • engineMark badges a tab row whose page isn't in Chromium.
  • Settings › Engines (components/settings/panes/Engines.tsx) is explanation only. Each engine keeps its own cookies, so people sign in again after a move.

What people see

  • Site Controls gets an Opens in row: a Chromium or WebKit pop-up for this tab, and Always open <site> in…, which writes a site rule.
  • Tab menu, page menu and command bar: Reopen in WebKit or Reopen in Chromium, and Always Open <site> in…. The command bar finds them by typing “engine”, “webkit”, “safari” or “chromium”.

  • Protected video prompt (when set to Ask): a popover under the address, “Play <host> in WebKit? This site's protected video doesn't play in Chromium.”, with Stay on Page, Open in WebKit and Don't ask again for this site, which writes a rule.
  • Mode switch: changing Pages open in shows “Switching…” in the row and moves open tabs (see Switching a page).

How a tab's engine is picked

The first rule that answers wins. store/engines.ts stays pure and tested, and every caller still asks it.

  1. Chromium-only pages always open in Chromium: bay:, chrome:, extension pages, DevTools, view-source: and the Chrome Web Store. So does any build without WebKit.
  2. Single-engine mode: in Chromium or WebKit mode, every page opens in that engine. In WebKit mode, a tab an extension opened or drives stays in Chromium, because extensions only exist there.
  3. The tab's own choice: an engine picked with Reopen in… stays with the tab, including after a relaunch.
  4. Opener: a link or pop-up opens in its opener's engine, as today.
  5. Site rule: the person's rule for the site.
  6. Streaming sites: when the list is on, those sites open in WebKit, as today.
  7. Default engine: Chromium unless the person changed it.

Typed addresses keep today's rule: they skip step 4, so a typed address follows its own site's rule or the default. If protected video then stalls in Chromium, the When protected video won't play setting decides: ask, move (today's behaviour) or stay.

Switching a page

  • A switch reuses lib/pageEngines.ts: it asks about unsaved work first, then sets tab.engine, and ContentCard keys the WebView by engine, so the other view loads the same address.
  • Keep the page in view: the old view stays on screen until the new one paints (first contentful paint, then two animation frames), with a 3-second deadline. Scroll position is read before the swap and restored once the page is tall enough. Page zoom is written to the other engine's per-host zoom.
  • Mode change: asks once when any open tab holds unsaved work, listing those tabs. The visible tab in each window switches now; background, pinned and slept tabs switch when next shown, so a big session doesn't reload all at once.
  • Back across engines keeps working (engineBack). A redirect chain still can't bounce a tab between engines (SITE_MOVE_SPACING_MS).

Bringing sign-ins along

Without this, switching engines signs people out, which makes the switch feel broken. When the setting is on, a switch copies the site's data from the engine it leaves to the one it opens in.

  • Scope: the tab's space profile and the site's registrable domain (accounts.example.com and example.com together). Cookies, HttpOnly cookies included, and localStorage.
  • Native work: Chromium needs a read and write of a profile's cookies for a domain in nncore (the missing pageCookies call), and WebKit needs the same through WKHTTPCookieStore on the profile's WKWebsiteDataStore in packages/nncore/ios/WebKit*.swift. Storage is copied by script in the page, before it unloads and after the new page commits.
  • Merge rule: a per-site ledger records what each engine last had, so only changes are carried. The newer value wins and removals carry over, which means signing out in one engine signs out the other on the next switch.
  • Never: private spaces, sites whose cookies the person blocked, or partitioned third-party cookies. A carry runs on a deadline and never blocks the switch. If it misses the deadline, the page loads signed out and the carry finishes for next time.

Acceptance

  • A new profile behaves exactly as today: Netflix opens in WebKit, everything else in Chromium, and a stalled DRM page moves.
  • WebKit mode: an ordinary site opens in WebKit; bay://settings, an extension's page and the Chrome Web Store open in Chromium.
  • A rule for figma.com set to WebKit opens it there from the command bar, a link and a pinned tab; removing the rule reverts it.
  • Reopen in Chromium on a WebKit tab survives a relaunch and keeps the scroll position and zoom.
  • A tab with a half-typed form asks before switching; Stay on Page keeps the text.
  • Signed in to GitHub in Chromium, Reopen in WebKit shows GitHub signed in; signing out there signs out Chromium on the next switch.
  • A private space never carries sign-ins; a site with blocked cookies never carries.
  • In WebKit mode, a news site shows no ads and its tracker requests are blocked; pausing blocking for the site brings them back.
  • Windows and Linux builds show no engine UI, and synced rules don't change their behaviour.
  • pnpm typecheck, pnpm test, pnpm lint and pnpm slop pass.

Risks

  • WebKit pages have no extensions and weaker ad blocking. Content rules (E7) cover network and element-hiding rules but not scriptlets, so some ads on some sites get through. The mode's footer says “no extensions”, and How engines differ explains the blocking gap.
  • Content rule limits. WebKit caps each compiled list and compiling takes seconds. Lists are compiled off the main thread, cached by version, and the previous compiled lists keep working until the new ones are ready.
  • Copied cookies are sensitive. They are copied in memory between the app's own stores, never written to a file, and never from a private space.
  • Sign-in flows that cross engines (OAuth pop-ups, SSO) can break if a rule sends the identity provider to the other engine. Links stay in their opener's engine, which covers most of these.
  • Memory: a mode change across a large session could reload dozens of pages at once. Lazy moves keep that to the visible tabs.

2. Passwords and passkeys from iCloud Keychain P1

Many Mac users keep their logins in Apple's Passwords app (iCloud Keychain), synced with their iPhone. Bay today fills only from its own Chromium store or a password manager extension. This item lets a space use the Mac's Passwords instead: logins, verification codes and passkeys, in Chromium and WebKit pages alike. Mac only; Windows and Linux keep Bay's store and extensions, and Chromium's Windows Hello passkeys already work there.

What Bay has today

  • Settings › Passwords: Chromium's password store per space, import and export, and a note on connecting 1Password, Bitwarden and others.
  • Bay-ICloudPasskeys.entitlements already asks for Apple's browser passkey entitlement (com.apple.developer.web-browser.public-key-credential) and Chromium's keychain groups. Apple hasn't granted it yet, so signed builds ship without it.
  • engine/patches/chromium-icloud-keychain-window.patch attaches Chromium's iCloud Keychain passkey sheet to Bay's own window.
  • WebKit pages hide PublicKeyCredential while the entitlement is missing; Settings › Engines shows the passkey access state.

What people see

  • Settings › Passwords › Password manager, per space: Bay (today's store), Passwords app (iCloud Keychain), or None (an extension handles logins). Spaces that share a profile share the choice, and the row says so.
  • Filling: with Passwords chosen, focusing a username, password or one-time-code field opens the Mac's own AutoFill panel under the field, the same one Safari shows. Bay stops offering to save logins in that space, and says why in the save prompt's place. Logins already in Bay's store still fill until the person exports them.
  • Verification codes: a page showing a setup QR code or an otpauth:// link offers Set Up in Passwords, which hands the link to the Passwords app.
  • Passkeys: one Passkeys row (Settings › Passwords, and the existing one in Settings › Engines) with the Mac's state: waiting for Apple's entitlement, not set up on this Mac, Allow Passkeys…, allowed, or turned off with a button to System Settings › Privacy & Security › Passkeys Access for Web Browsers. Once allowed, Chromium and WebKit pages both offer the iCloud Keychain passkeys.
  • Moving in: Export to Passwords… writes Bay's saved logins as a CSV the Passwords app imports, then offers to delete them.

How it works

  • The AutoFill panel: macOS shows its Passwords panel for native text fields. Chromium's fields aren't native, so the host tells AppKit which page field has focus and what kind it is (username, password, code). The page script already classifies fields for Bay's own autofill; that classification is shared TypeScript, and only the panel hand-off is Mac native code. The panel's insert goes back into the field through the page, as a paste would.
  • Passkeys in Chromium: Chromium's iCloud Keychain authenticator (ASAuthorizationWebBrowserPlatformPublicKeyCredential) needs the entitlement and the person's permission. The Passkeys row asks for that permission once (requestAuthorizationForPublicKeyCredentials), and the engine's iCloud Keychain preference is turned on for spaces that use it.
  • Passkeys in WebKit: WKWebView uses the same system passkeys once entitled; the hide-passkeys script is dropped then.
  • Choice storage: passwordManager on each space's profile settings, synced like other space settings. A None choice turns off Chromium's own save prompt for that profile (credentials_enable_service), so the extension's own prompt is the only one.

5. Decisions

Settled on 24 Nov 2026. The sections above already follow these.

Question Decision Why
WebKit mode and ad blocking Compile Bay's filter lists into WebKit content rules (E7) before WebKit mode appears. Until then the mode stays hidden; Automatic, Chromium and site rules ship without waiting. Built-in blocking is one of Bay's main promises. A mode that quietly turns it off would surprise people, and streaming sites gain blocking too.
Rule scope Key site rules by registrable domain, so a rule for example.com covers its subdomains. People think in sites, not hosts. Sign-in and media subdomains (accounts., www., CDN hosts) would otherwise split one site across two engines and break sign-ins.
Protected-video default Keep Move to WebKit. Ask and Stay are available in Settings. Automatic mode promises today's behaviour. Video that just plays beats a prompt for most people.
Per-space default engine Leave it out. Revisit only if people ask for it. Site rules and per-tab switches already cover the real cases. Another layer would make the order harder to explain and test, and sign-in carrying is per space already.
MCP reach (G1) An agent sees only the spaces ticked when it is approved. The current space is ticked by default, and private spaces are never offered. An agent reads signed-in pages, so access should be opt-in per space. Changing it later in Settings › Advanced keeps the cost of starting narrow small.

Known gaps

  • Nothing native is built yet: the engine (nncore, the Mac's Chromium) needs a rebuild for nn_cookies_site and nn_cookies_apply, and the app for the Swift changes. The C++ is syntax checked against the local Chromium tree.
  • A mode change asks about unsaved work per tab, when each tab moves, rather than once with a list of tabs.
  • A background tab a settings change left for later forgets the move if Bay quits first; it moves on its next settings change or pick.
  • The sign-in ledger lives for the app's run: after a relaunch, the first switch of a site copies cookies but carries no sign-outs.
  • Storage carries only localStorage of the page's own origin, written after the new page commits, so a page that reads it during load sees it on the next load.
  • No Reopen in… item in the app menu yet; the tab menu, Site Controls and the command bar have it.
  • Deceptive-site warnings apply to WebKit pages opened after the setting changes.
  • WebKit pages show no blocked count in Site Controls: content rules count nothing.
  • The Objective-C++ and Swift for E5–E7 are parse-checked only; the first Mac build may need small fixes.
  • G3's Windows and Linux dispatch (engine_services.cc) isn't syntax checked on the Mac (it needs generated mojom headers); content_blocker.cc is.
  • Spelling has no custom dictionary editor yet, and on Linux a language's dictionary downloads from Google's servers the first time, which the ungoogled engine may block.
  • Ask on Page needs pod install before the Mac build, so Expo registers the new BayAskPage module. It has no keyboard shortcut or menu item yet, and long pages are cut to fit the model's context.
