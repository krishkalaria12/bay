Mobile engineering plan · 17 November 2026 · base: PR #27 feat/phone-sync at bd495e62 · this plan's branch: refactor/mobile-native

Bay mobile, native: Swift on iPhone, Kotlin on Android, one Rust core

Rewrite apps/mobile (Expo SDK 58, React Native 0.88) as two native apps: SwiftUI for iOS and Jetpack Compose (Foundation only, no Material) for Android. Both apps sit on one shared Rust core, exposed through UniFFI, that owns the store, persistence, sync, address input and the other platform-free logic. The engines (WebKit, Bay's Chromium) and everything you see are native code.

PR #27's feature set is what the rewrite has to match: spaces with their own data, phone↔computer sync through the relay, the Settings screen, onboarding, reading and power tools, downloads, media, import, privacy and the app icon picker. The Expo app keeps shipping until the native apps pass the same checks on both platforms. Then it is removed.

This is a plan only, with no code changes. I've settled every open decision with my recommendation; the reasons are in §2.

2. Decisions (resolved with the recommended option)

Decision Choice Why, and what it rules out
D1How logic is shared One Rust crate, bay-mobile-core, with UniFFI bindings generated for Swift and Kotlin.

Rust already ships in both apps (the adblock engine), so the build already handles the toolchain, xcframework, NDK and the duplicate-symbol fix for the Chromium link. Mozilla's application-services uses this same pattern for Firefox iOS and Android's history, tabs and sync. That is the closest precedent to Bay's store and sync.

Rejected: Kotlin Multiplatform would add a third language runtime and GC on iOS, and its Swift export is still maturing. A headless JS runtime running today's TS would keep Hermes in a native app. Two hand-written copies would drift.

D2Core vs native boundary

core domain types, reducer, persistence, spaces, history, bookmarks, pins, site settings, preferences, sync (crypto, pairing, adapters, cycle), address input and suggestions, import parsing, settings tree and search, onboarding flow, the adblock engine.

native views, navigation, gestures, animation, both engines, keychain/keystore, files and pickers, downloads, media session, voice, widgets, share, notifications, the sync schedule.

Anything a test can run without a device goes in the core. Anything that touches an OS API or a pixel stays native. Fast UI state (load progress, scroll, gesture positions) never crosses the bridge.
D3Store shape The core owns a BrowserStore object. Native calls dispatch(action), which takes a UniFFI enum mirroring today's 55 actions. The core returns a Change (revision plus touched slices) and tells a registered observer. Each app keeps a thin observable mirror: Swift AppModel: ObservableObject and Kotlin StateFlows. The reducer stays the single source of truth, as it is now. Slices (tabs of a space, pins, preferences) are read on change instead of copying the whole state across FFI. Large lists (history) are paged queries, not part of the snapshot.
D4Persistence Revised in N1: the core reads and writes the Expo app's own document, browser.json (version 2), with the same repair rules, written atomically after the store is still for a moment. SQLite (rusqlite, bundled) comes later, if history and bookmark search or the save cost ask for it, with a one-time import from the document. The first native launch reads the file the Expo app left, with nothing to migrate, and the 446 recorded fixtures prove the port reads and changes it exactly as the TS store does. In Rust, serializing a few thousand entries off the main thread takes milliseconds, which takes away the main reason for SQLite.
D5Networking Revised in N2: the core declares an async HttpClient foreign trait (method, URL, headers, body in; status and body out). iOS answers it with URLSession, Android with HttpURLConnection. Everything above that line is Rust: the relay client, its JSON, retries, pairing, sealing. reqwest 0.13's TLS is rustls on aws-lc, a C library to cross-build for iOS and Android. Its certificate verifier also needs JNI start-up and an extra Kotlin component on Android. The native clients bring the OS's trust store, proxies and VPN for free and keep a TLS stack out of the binary. Rust tests answer the trait with an in-memory relay that behaves like apps/sync-relay.
D6Sync crypto Port packages/sync/src/relay to Rust using the crates that match today's @noble/@scure calls one for one: aes-gcm, hkdf, hmac, pbkdf2, sha2, x25519-dalek, bip39 (English word list; the 4-letter prefix rule stays our code), data-encoding (lowercase unpadded base32, base64url), getrandom, zeroize. Then check it it byte for byte against packages/sync/fixtures/golden.json, the vector the TS port and the Mac's Swift crypto already pass. Secrets go through a SecretStore foreign trait (Keychain / Android Keystore). One golden vector, three implementations, so the computer and phone can't diverge. The core never holds secrets at rest.
D7iOS UI and minimum SwiftUI, minimum iOS 15.0. UIKit where SwiftUI is weak on 15: the WKWebView host and page gestures, sheets (UISheetPresentationController, iOS 15) and the settings push stack. Liquid Glass through .glassEffect on iOS 26, and a material-blur fallback on 15–25.

You asked for about iOS 14. 15 is the lowest that works. Xcode 26 supports iOS 15 and up only, and Xcode 27 turns older targets into build errors. Tab restore needs WKWebView.interactionState, which is iOS 15+. iOS 15 runs on every iPhone that iOS 14 does (6s and later), so no device is lost.

What 15 costs: ObservableObject instead of @Observable (17), NavigationView/UIKit instead of NavigationStack (16). Per-space website data (WKWebsiteDataStore(forIdentifier:)) stays iOS 17+. Below 17 spaces share one store, which is already how the current guard works.

D8Android UI Jetpack Compose on compose.foundation, with no Material3 in UI modules. Headless sheets, menus and dialogs come from Compose Unstyled, styled by Bay's own design system. The Chromium view stays an Android View (the SurfaceView handover) inside AndroidView. Navigation 3 for the settings stack and predictive back. minSdk 29, as today, which Bay's Chromium build requires. This keeps the Arc-Search-for-Android look (flat translucent fills, hairlines, no ripples or elevation) that AGENTS.md requires. The Compose Material libraries would bring that styling back by default.
D9Starter bases Rust: ianthetechie/uniffi-starter layout. Android: android/architecture-templates (multimodule), using Now in Android's build-logic convention plugins. iOS: tuist init SwiftUI app, using tddworks/SwiftUITemplate as the reference for extension targets. Details in §4. Each starter supplies the skeleton only. We drop what Bay doesn't need (Room, Hilt, TCA, sample features).
D10Dependency injection and concurrency No DI framework. Each app has one hand-written AppGraph that builds the core, engine and services. Swift structured concurrency (actors for engine and downloads), Kotlin coroutines (lifecycleScope, Dispatchers.IO). Store calls are synchronous. Network and long-running work (sync, suggestions, import) are exported async on the core's tokio runtime (#[uniffi::export(async_runtime = "tokio")]), so Swift and Kotlin just await or suspend. The app has a dozen services, not hundreds, and Hilt/KSP would cost build minutes. Today's Effect runtime goes away: its failure and retry policies move into the core (for sync and import) and native services.
D10bRust crates Use crates.io crates freely wherever one saves work. Pick well-maintained crates (RustCrypto, the rusqlite/serde/tokio family, crates the adblock crate already pulls in). Write our own code only where the behaviour is Bay's: the reducer, sync record format, the address rules. The full list is in §4.1. Your call: crates make the port shorter and better tested than hand-written equivalents. Bay controls the size cost by building with LTO, opt-level = "s" for the core, and one Rust artifact per app (D16). cargo deny checks licences and advisories.
D11Strings One source catalog, packages/mobile-core/strings/<locale>.json, written from the TS tables by a script once (removed with the Expo app at N8; the JSON is the catalog now) and compiled into the core. The core's i18n module gives each app a locale's whole catalog (English behind missing keys), matches device tags, and fills {name} placeholders. Each app keeps the table in an observable Strings object. Revised in N0: this replaced generated xcstrings and strings.xml. Settings › Language switches the whole app at once, without a restart, as the Expo app does. Native resource files follow the system's per-app language and need a restart. One file per locale for translators, and the key and placeholder checks run once in Rust.
D12Design tokens and icons tokens.json (radius, space, icon sizes, row heights, type scale, colours from tokens.ts and global.css) generates BayTokens.swift and BayTokens.kt. Icons: SF Symbols on iOS, Material Symbols outline vector drawables on Android, each in a fixed square. This keeps the rule in today's AGENTS.md (“tokens, not numbers”) on both platforms, with one place to change a radius.
D13Page scripts They stay JavaScript in packages/mobile-pagescripts. A build step writes every script into one resource file (resources/pagescripts.json) that both apps bundle; a script with arguments reads them from args, declared ahead of it as JSON. The scripts are TypeScript in packages/mobile-pagescripts/src (moved from the Expo app at N8), one copy; a test fails when the resource is out of date. They aren't minified: no minifier is in the repo, and only Readability is large, which is compact already. Their jsdom tests keep running under Node. They run inside the page, so they can't be native. Sharing them as files keeps one copy.
D14Strategy Build the native apps beside the Expo app, then cut over. No brownfield React Native embed. The Expo app gets fixes only. Public test builds before 22 Dec 2026 (when Arc Search for Android goes away) still come from the Expo app. The browser screen is one large component, so screen-by-screen embedding would mean running two UI stacks in one app for months. The native rewrite isn't allowed to block the December test builds.
D15Where it lives apps/ios, apps/android, packages/mobile-core (Rust, with packages/adblock as a dependency), packages/mobile-pagescripts, on refactor/mobile-native, stacked on #27. Same bundle ID and application ID (in.krishkalaria.bay.mobile). The native apps install over Expo builds and keep users' data (§9). Stack rule as before: merge lower branches up, never rebase.
D16One Rust library per app The core links the adblock crate, and each platform ships one Rust artifact. On iOS one xcframework replaces BayAdblock.xcframework. On Android, libbay_engine.so links the core staticlib in place of libbay_adblock.a, keeping the llvm-objcopy --weaken step. Two Rust staticlibs in one binary duplicate the Rust standard library's symbols. Android already hit this with Chromium.
D17Desktop Out of scope. The core is written so the Mac (Swift bindings) or the Windows/Linux ports could adopt it later. Desktop keeps @bay/core and @bay/sync in TS. Sync compatibility comes from the shared golden vector and record format, not from shared code.

6. Core API sketch

This is the shape of the boundary, not final signatures. UniFFI proc-macros, library mode.

// packages/mobile-core/crates/bay-core/src/lib.rs
// Networking is internal: reqwest + rustls on the core's tokio runtime (D5).
#[uniffi::export(with_foreign)]
pub trait SecretStore: Send + Sync { fn read(&self, key: String) -> Option<Vec<u8>>; fn write(&self, key: String, value: Vec<u8>); }
#[uniffi::export(with_foreign)]
pub trait StoreObserver: Send + Sync { fn changed(&self, change: Change); }

#[derive(uniffi::Object)] pub struct BrowserStore { /* db, state, observers */ }

#[uniffi::export]
impl BrowserStore {
    #[uniffi::constructor] fn open(dir: String, legacy_json: Option<String>) -> Result<Arc<Self>, StoreError>;
    fn dispatch(&self, action: Action) -> Change;          // Action: 55 variants, mirrors BrowserAction
    fn tabs(&self, space: String) -> Vec<Tab>;
    fn spaces(&self) -> Vec<Space>;  fn pins(&self, space: String) -> Vec<PinnedSite>;
    fn history(&self, space: String, query: String, page: u32) -> HistoryPage;
    fn preferences(&self) -> Preferences;
    fn observe(&self, observer: Arc<dyn StoreObserver>);
}

#[derive(uniffi::Object)] pub struct PhoneSync { /* store, http, secrets */ }
#[uniffi::export(async_runtime = "tokio")] impl PhoneSync {
    async fn join_with_code(&self, code: String) -> Result<Pairing, SyncError>;   // returns 4 check digits
    async fn join_with_phrase(&self, words: Vec<String>) -> Result<(), SyncError>;
    async fn cycle(&self) -> Result<SyncReport, SyncError>;
    fn status(&self) -> SyncStatus;  fn set_types(&self, types: SyncTypes);  async fn leave(&self) -> Result<(), SyncError>;
}

#[uniffi::export] fn parse_input(text: String, engines: EngineSet) -> Input;   // from @bay/core input.ts
#[uniffi::export] fn settings_search(query: &str, ctx: SettingsContext) -> Vec<SettingsMatch>;

Swift sees BrowserStore.open(dir:legacyJson:), store.dispatch(action: .closeTab(id:)). Kotlin sees BrowserStore.open(dir, legacyJson), store.dispatch(Action.CloseTab(id)). Errors become Swift Error types and Kotlin exceptions.

7. Phases

Core (N1–N2) and engine hosts (N3) don't depend on each other and can go in parallel after N0. UI phases need both.

Commit in chunks. Don't wait for a phase to finish, and don't commit every small edit. Commit once a good amount of work is done and checked: a ported core module with its tests passing, an engine host browsing on both devices, a screen that matches the Expo build on iOS and Android with its e2e flows passing.

  • Before each commit, run lint, typecheck and the slop check (repo AGENTS.md), plus cargo test/clippy for core changes and the Swift and Kotlin builds for app changes.
  • Each commit stands on its own and builds. Messages are one line, for example feat(mobile-core): port the store reducer or feat(ios): add the tab switcher.
  • Push after each chunk so refactor/mobile-native and its PR show progress. Record any gap a chunk leaves open in Known gaps in the same commit.

9. Users' data across the cutover

Update, 19 November 2026: the mobile app never shipped, so there are no users' data to carry over and the native apps keep no fallbacks for the Expo app's layouts. Secrets (the sync key, saved sign-ins) live in Bay's own keychain service and keystore preferences. The plan below is kept for the record.

The native apps keep the same bundle ID and application ID, so they install as an update. On first launch:

  1. Browser state: the core opens browser.json in the app's document directory (expo-file-system Paths.document) as the Expo app left it, and keeps writing the same version-2 document (D4).
  2. Sync state: import sync/state.json the same way. The sync key is read from where expo-secure-store put it. On iOS that's the Keychain under its service name. On Android it's the expo-secure-store SharedPreferences file, encrypted with its Keystore alias. Write the key back through the native SecretStore, then remove the old entry. The exact service names and aliases are checked against the expo-secure-store source in N1.
  3. Engine data: WebKit data stores (default + forIdentifier per space) and the Chromium profiles under Spaces/<id> stay where they are. The new engine hosts open the same identifiers and paths, so cookies and logins survive.
  4. Tab state and snapshots: same cache paths as BayEngineModule uses today. If they're missing, tabs reload instead of failing.
  5. Preferences that live in the OS: alternate app icon (iOS keeps it; on Android, map the Expo activity-alias names to the new ones), default-browser role.

Migration runs once and is tested in N7 on all three test devices. If the import fails, the old files stay and the app opens with a fresh state plus a notice. A partial import never runs.

10. Risks

Risk What we do about it
Rust std symbols clash with Chromium's on Android One staticlib (D16), the existing --weaken step, and a local NDK test link before any runner build.
The reducer port differs in small ways Differential fixtures generated from the TS reducer. The TS reducer stays in git history as the reference until N7.
Sync crypto mismatch locks phones out Golden vector gate in N2, and a real-relay round trip with the stand-in computer before any UI work on sync.
SwiftUI on iOS 15 lacks newer APIs UIKit for sheets, navigation and the web view host. The #available branches are listed in BayDesign. Test on an iOS 15 simulator runtime every batch.
Compose without Material means writing more components Compose Unstyled for behaviour, our own styling. The component list is bounded by today's src/chrome.
Rewrite time competes with the December test builds D14: test builds ship from Expo. The native work doesn't touch apps/mobile except to fix it.
Two UIs drift Same as today (AGENTS.md “Both platforms, always”), plus shared tokens and strings and identical e2e flows on both.
Binary size The core replaces the adblock artifact. It adds the store, SQLite, tokio, reqwest/rustls and the crypto crates, but React Native, Hermes and the JS bundle go away. LTO, opt-level = "s", panic = "abort", trimmed crate features. Measured in N7 with cargo bloat.
Crate churn or licences cargo deny (licences, advisories, duplicate versions) in CI. Pin versions in Cargo.lock and upgrade on purpose.
UniFFI async and callback edge cases Keep async to network and import work on the core's tokio runtime. Observers are fire-and-forget with a revision number, so a missed call is recovered by the next read.

Known gaps

Add parity gaps here in the commit that finds them.

  • iOS: Argent's tree still lists the active page's web content under the tab switcher, although every page view is hidden there (WebKit's remote accessibility tree). VoiceOver and taps aren't affected; tests should target identifiers, not page text, while the switcher is up.
  • The e2e flows are in apps/mobile-e2e. N4's flows pass on Android; two steps there changed for the native labels: an archived row's label is "Open <title>" with the site as its state, and a bare title also matches the row's Remove button.
  • The e2e flows predate the longer page menu: fresh-start waits for page-settings, which is now below the menu's fold, and start-page taps page-pin before the sheet has settled. smoke passes; the flows that open the page menu need a scroll and a settle step.
  • iOS 15 and 16 weren't run: Xcode 27.2 offers no simulator runtime older than iOS 27. The app compiles for the 15.0 deployment target, and the iOS 15 paths (materials in place of glass, older toggles and sheets) were only read, not run.
  • Google's Accessibility Scanner app wasn't run on Android (it needs a Google sign-in); the same checks run in the audit test.
  • iOS: the widgets weren't placed on the simulator (automation can't add one); the bay:// links they send were checked instead. Links to http/https pages go to Safari on a debug build, which can't be the default browser; they take the same path as the share extension's links, which were checked.
  • iOS builds claim the default-browser entitlement only with TUIST_BAY_DEFAULT_BROWSER=1 (as the Expo app's BAY_DEFAULT_BROWSER); without it the welcome skips the links page and Settings says Bay can't be the default.
  • iOS: the e2e flows can't run through Argent's runner, which reads a projected UIView tree where SwiftUI's accessibility identifiers don't appear (describe and await-ui-element do see them). N5's flows were checked by hand on the iPhone simulator instead: import (paste, steps, the file picker opening and cancelling; choosing a file in the out-of-process picker doesn't take Argent's taps), the app icon, sync pairing, Inspect, Reader and the bottom inset.
  • iOS before 26: WebKit has no obscured inset, so the page's scroll view is inset under the bar but what a page fixes to its bottom (YouTube's tab bar, say) still sits under Bay's bar, as it did in the Expo app.
  • iOS: Argent's tree still lists the page's web content under Settings and sheets, although the page views are hidden and marked accessibilityElementsHidden (WebKit answers accessibility from its own process).
  • Android e2e: on a loaded emulator, the runner's Enter can reach the address field before the keyboard's last characters, so the page opens a shortened address. Go waits a moment for pending edits; a slower run can still lose the tail. A person's Go comes from the keyboard, in order.
  • Android: the link menu has no live preview of the linked page. A second page view drawing over the tab leaves the tab blank once it goes, even after the view is disposed (which hands the compositor back), the tab is shown again or re-attached; the engine's hand-back needs fixing before the preview can come back. iOS has the preview.
