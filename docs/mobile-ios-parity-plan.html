Bay mobile: iOS parity and missing features

Plan · 5 November 2026 · based on the code on main at d4565541 and Arc sources from the web · adds to docs/mobile-plan.html, which stays the roadmap

Updated 7 November 2026: I1–I6 are now done in code (see Since the plan); still to verify on a device, like everything below. Earlier: 6 November 2026 against main at 47589d3b, after PRs #12 and #11 landed.

iOS has a much shorter list of gaps than expected: five feature gaps and one design gap. The larger gaps are on both apps, and several of them will break everyday sites.

Since then, Google sign-in (B1) has a fix in code on both apps, and as of 7 November all six iOS gaps are done in code: system media controls (I1), background downloads with resume and a finished notification (I2), page dialogs (I3), the link menu (I4), ad blocking accepted as an engine limit (I5) and Liquid Glass sheets with haptics (I6). None of the new iOS code has been compiled on a device yet.

Why iOS may feel less finished

  • Apart from the bottom bar and a few glass panels, iOS draws the same React Native sheets and switcher as Android. It can look like Android with glass buttons.
  • The native code is smaller: 967 lines of Swift against 1,259 of Kotlin on 5 November, and 1,160 against 1,748 now that Android downloads files itself. Part of that is real gaps, and part is WebKit doing the work for free.
  • The two commits tagged mobile(android), pinch to zoom and two-finger handling, were Android catching up to what WebKit already gives iOS.

Limit of this audit: I read the code and did not run either app. This checkout has no ios/, android/ or node_modules, and Argent listed no simulators. If you've seen something broken on an iPhone, it may not be listed here. Stage 0 exists to catch that.

Found on the real phone, which reading the code couldn't show

  • Every Android download sat at "pending": DownloadManager runs as a JobScheduler job, and the system holds those jobs back while the phone is warm (thermal status "moderate", common while charging on mobile data).
  • On Android 13 and later Bay showed no notifications at all, the I1 media notification included, because it never asked for POST_NOTIFICATIONS.
  • URLUtil.guessFileName saved a film as "www.bin". Names now come from Content-Disposition or the address.

Still unverified: none of #11's Swift has been compiled. It only passed swiftc -parse, and the iOS 26 BGContinuedProcessingTask calls are the riskiest part. pnpm e2e wasn't run for either PR. Stage 0 now starts with an iOS build.

What Arc mobile tells us

There were two apps. Arc's first iPhone companion was the desktop sidebar in your pocket: Spaces, pinned tabs and near-real-time sync. Arc Search replaced that idea with a fast, minimal browser, then gained Arc Sync for Spaces, pinned tabs and Today tabs. Arc is now being shut down, and that changes what's worth copying.

  • 22 October 2026 (passed) Arc Search can export open tabs. New Arc accounts ended.
  • 23 November 2026 (17 days away) Browse for Me and other AI features turn off on both apps. Sign-in and sync end.
  • 22 December 2026 (46 days away) Arc Search for Android is removed from Google Play and, per reports, from phones. Arc stops working on Mac and Windows. Only a lite iPhone app remains.

The opening: Android users of Arc Search lose the app in 46 days, and the company's replacement, Dia, has no announced phone app. Bay's Android design already follows Arc Search. A public test build before 22 December is the best-timed thing in this plan. That's decision D1, and the one to look at first.

The one new shared piece: Page requests

Four separate gaps are the same shape: a page asks a question and waits for the person to answer. They are alert/confirm/prompt (I3), location, camera and microphone (B7), HTTP sign-in (B3), and "open this in another app?" (B5). Build one engine event, onPageRequest, one call, answerPageRequest(id, answer), and one shared sheet. Each native side only holds the completion handler until the answer arrives. It also keeps the promise of one design with no Material on Android, and each site's answers can feed per-site settings (B12) later.

Decisions

You asked me to settle the open questions with my recommendation, so these are decided unless you say otherwise.

# Decision Why
D1 Public test builds of both apps before 22 December, on the system WebView. Our Chromium still comes before the full store release. This changes the current order, where phase 8 follows phase 7. Arc's date won't wait for a Chromium build, and the swap sits behind @bay/engine anyway. Full release order stays as you chose it.
D2 Fix sites first, then add features: stages 0, 1 and 2 come before Peek, widgets or voice. A browser that can't sign in or upload a file loses people faster than one with no widget.
D3 Page requests is one shared sheet, not native alerts on each side. It fits your one-design rule, covers four gaps, and avoids Android's Material dialogs.
D4 iOS ad blocking stays on WebKit content rules. A web view can't intercept subresources on iOS, so full parity isn't possible. Measure it rather than chase it.
D5 Glass on iOS sheets; contents stay shared. It closes the look gap for little code and keeps your shared-panels decision.
D6 No Browse for Me, Pinch to Summarize or Call Arc. Arc is turning them off, Lens has none, they need a paid server, and they conflict with a browser that keeps data on the device. Copy as Markdown already covers taking an article elsewhere.
D7 Sync, Spaces and tablets stay after the first release. Set supportsTablet: false until then. This keeps your existing decision. A portrait-only iPad build invites App Store problems for no benefit.
D8 On-device translation stays last. Google Translate links stay until then. This keeps your existing decision. The mirror for Mozilla's files still needs your go-ahead before anything is published.

Risks

Risk Response
This audit comes from reading code, so some gaps may behave differently when run. Stage 0 runs first and corrects this file.
Real new windows (B19) are the hardest item: WebKit needs a view returned synchronously, while React mounts tabs itself. Do it last in stage 2. If it blocks, fall back to opening a new tab without an opener and list the sign-ins that fail.

#11's iOS code has never been compiled, and BGContinuedProcessingTask is new in iOS 26. Build it before anything else in stage 0. Without the plugin's BGTaskSchedulerPermittedIdentifiers entry, Bay skips the task rather than crash, so an old prebuild falls back to background time.
Our Now Playing info may conflict with WebKit's own. Test on a real iPhone before writing any code (I1).
New work on the system WebView gets replaced in phase 7. Stay behind @bay/engine and let e2e tests prove the swap.
Store timing. I recall Google Play requiring newer personal accounts to run a 14-day closed test with 12 testers first. I didn't verify this. Check the account type now. If it applies, the closed test has to start by about 1 December.
