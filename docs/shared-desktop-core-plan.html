One desktop core for macOS, Windows and Linux

Write each piece of Bay's desktop logic once. Chromium glue moves into the portable C++ target both hosts already link. Platform-neutral data work (filter lists, sync crypto, browser import) moves into Rust crates that the phone apps share. Parity checks keep the copies from coming back. A last phase decides whether macOS moves onto the WebUI host as well.

Drafted 24 Nov 2026 against main at 4be8f6715. Windows and Linux are built and pass runtime acceptance. Work happens on refactor/shared-desktop-core; Progress says what is built. Line counts are tracked files without fixtures or vendored code, rounded.

Known gaps

  • Windows and Linux builds. Neither engine has been built with these changes. Start a windows-build-N and a linux-build-N run, then check the blocker on both: first launch offline, a list turning on, a paused site, Settings › Privacy.
  • Contract coverage isn't built. Reading the methods out of the sources doesn't work: the WebUI host registers them at run time across many files, and the Swift modules don't all use one pattern. It needs a runtime report instead: each host lists what it registered (the web host's getNativeHostInfo, the Expo modules' exports), checked by the acceptance scripts.
  • Recorded outputs. Only the sync vector is in place. The import Wire JSON per fixture profile still has to be recorded from both readers before Phase 3.
  • SQLite link spike for bay-import isn't done (decision 1).
  • The request filter's hot path (Filter, Response, the body and header filters, HostOf, Covers) is still written twice, in NNCoreContentBlocker.mm and content_blocker.cc. It needs only the C ABI and the standard library, so one shared C++ header could serve both.
  • Two catalogue copies. filter_lists.json still ships from packages/chromium/ios and the phones keep their own in bay-core; one file in bay-lists remains to do.
  • Sync vaults. Reading and writing the vault folder is still written twice: Swift coordinates iCloud Drive (NSFileCoordinator, .icloud placeholders) and C++ reads plain files. The listing rules (pending, damaged, present) could move into bay-sync with a hook for how each host opens a file.
  • Recovery kit QR. Decision 2 has Rust give the QR matrix; macOS still draws it with Core Image and Windows and Linux with vendored qrcodegen.
  • Phrase typing. macOS now reads a typed phrase as Windows, Linux and the phones do: ASCII letters only. Before, any Unicode letter counted, so an accented letter could join two words where it now separates them. No valid phrase reads differently.
  • Phones. bay-core (PR #31) still has its own copies of the sync keys, phrase and base32; it takes bay-sync by path once both land.
  • Dependency builds. Cargo builds every crate type a dependency lists, so bay-adblock's cdylib is linked whenever bay-desktop builds. The runners have linkers, so this costs time, not correctness.

2. What goes where

One rule for every piece of code that moves, and for new code from now on.

Code that… Goes in Why
calls Chromium's C++ API //bay/core:portable (C++) Rust can't call Chromium's C++ classes (permissions::PermissionPrompt, chooser controllers, extensions::). Both hosts already link this target: webui/BUILD.gn depends on it.
does platform-neutral data work in native code A Rust crate Parsing, crypto, file formats and list bookkeeping get one implementation for three desktops and two phone apps, tested against shared fixtures.
runs per keystroke or render, or is UI logic TypeScript (@bay/core, apps/browser) It's already shared by every desktop. A native hop would put it behind an async bridge (Mojo on Windows and Linux, Expo calls on macOS) for no gain.
calls an OS API A platform adapter (Swift, _win.cc, _linux.cc) Keychain, DPAPI, Secret Service, file pickers, EventKit and the like. Kept thin.

Rust crates don't do networking, threads or timers. They don't open sockets, start threads, keep timers or read OS settings. The host fetches, schedules and stores secrets, then hands bytes and the current time in. That keeps each host's networking (SimpleURLLoader, NSURLSession), threading and sandbox rules as they are. They may read and write their own files in a folder the host names, off the host's main thread: that's where most of the duplicated code was.

4. Phases

Phase 0 comes first. Phases 1 to 3 each need it and are independent of each other. Phase 4 doesn't touch Rust and can run alongside them. Phase 5 begins in Phase 0 and grows with each phase. Phase 6 is a decision made after 1 to 4, which shrink its work whichever way it goes.

  1. Groundwork: workspace, one static library, renames, contract coverage, recorded outputs
  2. Filter lists into bay-lists: smallest move, the crate is already linked everywhere
  3. Sync into bay-sync, with no format change
  4. Browser import into bay-import
  5. Chromium glue into //bay/core:portable
  6. Parity guards in CI and in AGENTS.md
  7. One host? A spike, then go or no-go on macOS running the WebUI host

Phase 0 · Groundwork

first
  1. A desktop Cargo workspace. Add packages/rust/Cargo.toml, with the new crates as members and bay-adblock as a path dependency. This follows mobile-core, which has its own workspace and takes ../adblock by path. A single root workspace would need every crate as a member, would move packages/adblock/target (which the mobile and Android scripts read), and would clash with mobile-core's workspace. Each workspace repeats adblock's [patch.crates-io] and release profile (opt-level = "s", LTO, one codegen unit, panic = "abort", stripped debug info), because Cargo applies both only from the root. bay-adblock gains the lib crate type and a public ffi module, the same change PR #31 makes.
  2. One static library per desktop. Add bay-desktop, a staticlib that re-exports bay-adblock's C functions and will carry each new crate. Headers stay hand-written, one per crate, as bay_adblock.h is today. Two Rust static libraries in one binary each bring their own copy of Rust's standard library, and their symbols clash. Mobile avoids this the same way, linking the blocker into bay-core through its adblock feature.
  3. Point both hosts at it. scripts/engine.py builds bay-desktop instead of the adblock crate (same cargo rustc --locked --release --lib --crate-type staticlib, +crt-static on Windows). webui/BUILD.gn links bay_desktop.lib / libbay_desktop.a. engine/chromium/apply.py copies bay_desktop.h instead of bay_adblock.h. On macOS, packages/chromium/scripts/adblock.sh and BayNNCore.podspec build and link the same crate.
  4. Rename the shared C++. packages/sync/windows → sync/portable and packages/import/windows → import/portable. bay/data/BUILD.gn already builds both on Linux.
  5. Contract coverage. Extend packages/platform/scripts/native-contracts.mjs to list, for each of the 321 methods, whether the macOS host and the WebUI host implement it, from what each host registers at run time (Known gaps says why not from the sources). CI fails when a method has no implementation on a platform and no capability saying it's unsupported there. Today nativeContracts.test.mjs only checks that every module has a contract.
  6. Record today's answers before moving anything. Save as golden files: the import Wire JSON for every profile in packages/import/fixtures, from both the Swift and the C++ readers; the filter-list state after a scripted series of events (first launch, toggles, an update, a failed fetch); and the sync vector, moved to packages/sync/fixtures/golden.json, the path mobile-core's README already names. Where the Swift and C++ outputs differ, record which one is right before Phase 3.
  7. SQLite link spike for bay-import. See decision 1.
Done when
CI builds libbay_desktop for macOS arm64, Windows x64 and Linux x64. The blocker behaves exactly as before on all three, and the coverage report runs in CI.

Phase 5 · Parity guards

from 0 onward
  • Contract coverage from Phase 0 fails CI on a method missing from one host.
  • TypeScript and Rust answer alike. Mobile-core's fixtures/*.jsonl were recorded from @bay/core's tests and, per its README, nothing records them any more. Add a recorder (scripts/record-core-fixtures.mjs) that rewrites them from the TypeScript tests in CI, so a TypeScript change shows up as a failing Rust test until the port matches.
  • Rust in every check job. cargo fmt --check, cargo clippy -- -D warnings and cargo test for the workspace in ci.yml, windows-checks.yml and linux-checks.yml, and in the pre-push hook next to lint, typecheck and slop.
  • Write the rule down. Add the section 2 table to AGENTS.md: new platform-neutral native logic goes in a crate, new Chromium glue in //bay/core:portable.

Phase 6 · One host for all three?

decision after 1–4

Windows and Linux are built and pass runtime acceptance on the WebUI host. The last split is the host itself. Running macOS on it would write each contract method once and leave a single JS runtime model. This phase is a spike and a decision, not a commitment.

6. Acceptance

  • Every golden file from Phase 0 still matches, from cargo test and from each host.
  • A sync chain made on any of the three desktops or a phone opens on every other one. Existing chains survive the update on each OS.
  • Imports from every fixture profile and from a real Chrome, Firefox, Arc and Zen install give the same result as the current release on each OS.
  • The blocker passes its first-launch, list, pause and cosmetic checks on each OS.
  • Each moved prompt works on each OS: permissions, choosers, cast, autofill and passwords, extension installs, screen sharing, context menu.
  • The contract coverage report shows no unexplained gaps.
  • The signed macOS candidate and its Sparkle update pass as docs/releasing.md describes. App and engine size changes are measured and noted in each phase's commit.
  • pnpm lint, pnpm typecheck, pnpm slop, pnpm test and the cargo checks pass.

7. Risks

Risk Mitigation
Saved data stops opening No format changes in this plan. Golden files are recorded before each move, and each phase keeps the old reader's tests until the new one matches.
Rust symbols clash One bay-desktop archive per binary. On Windows and Linux the engine also carries Chromium's own Rust std; scripts/engine.py already renames the one clashing symbol (rust_eh_personality) and keeps doing so for the new archive.
Two SQLites Chromium ships its own renamed SQLite and the macOS app links the system one. Phase 0's spike settles it (decision 1).
Size grows RustCrypto sits beside BoringSSL, and regex crates beside RE2. Keep the size profile and LTO, measure the archive per phase, and never trade away features for size (AGENTS.md).
Secrets linger Secret retrieval stays in the host. Rust receives only the unlocked key, in zeroize buffers.
Mobile branch not merged The desktop crates don't depend on PR #31. bay-core takes the desktop crates by path and drops its copies after it merges.
Hosts drift during the move Each phase lands per area, both hosts in the same commit, so main never has one host on the new code and the other on the old.
One host loses Mac polish Phase 6 is gated on measurements, and nothing earlier depends on it.

8. Stays per platform

  • OS adapters: secret stores, file pickers, notifications, autostart, default browser, tray and dock, window frames (Mica, GTK, macOS).
  • The WebKit engine and the Apple Intelligence features (Tidy Tabs, Tidy Names, inline completion), which stay macOS only.
  • Safari direct import, Full Disk Access and Dia's Apple Events.
  • Installers and updaters: Sparkle and DMG, winget and MSIX, AppImage, deb, rpm, tarball and AUR.
  • UI logic and per-keystroke work, which stay in TypeScript (section 2).

9. Decisions

Decided 24 Nov 2026; each takes the recommendation this plan made.

  1. SQLite for bay-import: bundled in the crate (rusqlite with bundled), provided the Phase 0 link spike shows no clash with Chromium's renamed copy or the system library on macOS. If it clashes, the host opens a read-only snapshot and passes rows in.
  2. Recovery kit drawing: stays native per OS, as today. Rust gives the kit's words and QR matrix.
  3. Desktop input: address input and suggestions stay in TypeScript on desktop. The phones' Rust port is held to it with shared fixtures (Phase 5).
  4. Phase 6 bar: every measure no worse than today's Mac build, and a Netflix tab working in WebKit. No margins.
  5. Crate boundaries: separate crates, one per area, re-exported by the single bay-desktop archive.
