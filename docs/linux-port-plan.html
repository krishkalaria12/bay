Bay for Linux

Linux is the third desktop target, and it differs from the other two in one important way: React Native has no usable Linux platform. Linux shares the Windows plan's host: Bay's React UI runs on react-native-web as a Chrome WebUI page, tabs are SurfaceEmbed elements in it, and the engine is NNCore, Chrome plus Bay's layer. Zen and Vivaldi are both built this way. The plan begins with what the Linux machine needs, including the commands to build the pinned Chromium. The phases follow.

Summary

Yes, Bay can run on Linux, on the same host as Windows. Since 17 October 2026 the Windows plan renders Bay's UI inside the engine: the React UI runs on react-native-web as a Chrome WebUI page (chrome://bay), each tab is an <embed> backed by Chromium's SurfaceEmbed, and the engine is NNCore, which is Chrome plus Bay's layer, as on macOS. Linux uses that host unchanged. Only the window frame, the backdrop and system integration are Linux code.

Why this fits Linux. Meta ships no React Native for Linux, and the community projects are early: react-native-linux says "pre-alpha, M0 done", and react-native-gtkx has no releases. Neither can embed a Chromium surface. A UI drawn by the engine needs neither, and Chrome's own window code already runs on Wayland and X11 through Ozone. This is the model Zen uses on Gecko: about 178k lines of UI JS/CSS, of which only 18 references are Linux-specific.

Upstream is building it. Chromium's WebUI Browser (kWebium) and components/surface_embed are both in Bay's pinned tag, 154.0.8037.58, switched off by default. One caution for Linux: upstream's SurfaceEmbed render test is disabled on Linux (crbug.com/534291359) while it runs on Windows and macOS. Phase 2 tests painting on Wayland and X11 before anything else.

Shared with Windows: the web build of the UI, the @bay/platform web wrappers, the asynchronous bridge over Mojo, the NNCore .mm split, the Bay window class and chrome://bay. Each is written once, in the Windows plan's phases, and Linux adds its frame, backdrop, secrets and packaging. The prerequisite steps below build stock Chrome from the pinned tree, which is the baseline both platforms start from.

Prerequisites & engine build

Do this first on the Arch box. Steps 1–3 prepare the host. Steps 4–8 run inside an Ubuntu 24.04 distrobox that shares your home directory, so the 100+ GB tree lives on the host disk. Ubuntu is the distro CEF documents, the one install-build-deps.sh supports, and the one GitHub's Linux runners use. Helium builds the same way, but in a Debian trixie container. Chromium's Debian sysroot (use_sysroot=true) makes the binaries independent of the build host's libraries, so an engine built here also runs on older distros.

The build in Steps 4–8 is a stock Chrome baseline with the exact pins from engine/patches/build/engine-lock.json. It proves the machine and toolchain work. The Bay-patched build uses the same checkout once Phase 1 adds linux to the series and the engine script (Step 9).

Commands, step by step

  1. Check the machine host · Arch

    nproc; free -h; df -h "$HOME"            # threads, RAM + swap, free disk

    Under 32 GB of RAM, add swap before the Chromium build, or its link steps get killed for running out of memory. On btrfs, create the file with sudo btrfs filesystem mkswapfile --size 16g /swapfile instead of the first line. 

    sudo fallocate -l 16G /swapfile && sudo chmod 600 /swapfile
sudo mkswap /swapfile && sudo swapon /swapfile

  2. Install host packages host · Arch

    No compiler here: Chromium brings its own clang, and the container provides the rest.

    sudo pacman -Syu --needed base-devel git python podman distrobox nodejs npm
sudo npm install -g pnpm@11.1.3          # matches packageManager in package.json

  3. Clone Bay and run the JS checks host · Arch

    git clone https://github.com/krishkalaria12/bay.git "$HOME/code/bay"
cd "$HOME/code/bay"
git switch feat/windows && git switch -c feat/linux
pnpm install --frozen-lockfile
pnpm typecheck && pnpm test

  4. Create the build container host → container

    distrobox create --name bay-engine --image docker.io/library/ubuntu:24.04 \
  --additional-packages "git curl file lsb-release procps python3 python3-pip sudo xz-utils zstd"
distrobox enter bay-engine               # same $HOME, same user; run Steps 5–7 in here
    Alternative: build directly on Arch, without a container

    This works because the sysroot supplies the target libraries, but Chromium doesn't officially support it and rolling-release Python or tools can break older build scripts. Use the package list from Chromium's Linux build instructions in place of install-build-deps.sh, then run Steps 5–7 on the host and skip the install-build-deps line in Step 6. 

    sudo pacman -S --needed base-devel python perl gperf nss alsa-lib glib2 gtk3 \
  nspr freetype2 cairo dbus xorg-server-xvfb xorg-xdpyinfo lsb-release

  5. Fetch the pinned tools container

    Every pin is copied from engine-lock.json, the same pins the Windows engine script uses.

    export CB="$HOME/chromium-build"
mkdir -p "$CB/automate" "$CB/chromium_git" "$CB/logs"

git clone https://chromium.googlesource.com/chromium/tools/depot_tools.git "$CB/depot_tools"
git -C "$CB/depot_tools" checkout --detach ccecefb58648ac0a416756b0a4591ec8905a7f55

git clone https://github.com/ungoogled-software/ungoogled-chromium.git "$CB/ungoogled"
git -C "$CB/ungoogled" checkout --detach 800d0bb5078472e4442c1fd73373172754a60939   # 154.0.8037.57-1

curl -fL --retry 3 -o "$CB/automate/automate-git.py" \
  https://raw.githubusercontent.com/chromiumembedded/cef/564dd6c4aafff558154bd3176eb5d13551db6734/tools/automate/automate-git.py

cat > "$CB/env-linux.sh" <<'EOF'
export CB="$HOME/chromium-build"
export PATH="$CB/depot_tools:$PATH"
export DEPOT_TOOLS_UPDATE=0 DEPOT_TOOLS_METRICS=0
export CEF_USE_GN=1 GN_OUT_CONFIGS=Release_GN_x64
export GN_DEFINES='is_official_build=false is_debug=false is_component_build=false target_cpu="x64" use_sysroot=true is_cfi=false use_thin_lto=false chrome_pgo_phase=0 dcheck_always_on=false symbol_level=1 blink_symbol_level=0 v8_symbol_level=0 proprietary_codecs=true ffmpeg_branding="Chrome" enable_widevine=true enable_mse_mpeg2ts_stream_parser=true use_vaapi=true rtc_use_pipewire=true treat_warnings_as_errors=false fatal_linker_warnings=false disable_fieldtrial_testing_config=true enable_hangout_services_extension=false enable_remoting=false use_official_google_api_keys=false google_api_key="" google_default_client_id="" google_default_client_secret="" enable_updater=false'
EOF
source "$CB/env-linux.sh"
"$CB/depot_tools/ensure_bootstrap"      # one-time cipd/python bootstrap, no self-update

    The GN args mirror gn_defines.sh (macOS) and GN_ARGS in scripts/windows/engine.py, plus Helium's Linux choices (use_sysroot, use_vaapi, rtc_use_pipewire). branding_file_path is left out because the stock tree doesn't have Bay's branding file yet.

  6. Download CEF + Chromium, then the build deps container · 1–3 h, network-bound

    source "$HOME/chromium-build/env-linux.sh"
python3 "$CB/automate/automate-git.py" \
  --download-dir="$CB/chromium_git" --depot-tools-dir="$CB/depot_tools" \
  --branch=8037 --checkout=564dd6c4aafff558154bd3176eb5d13551db6734 \
  --no-chromium-history --x64-build --no-debug-build --no-build --no-distrib \
  2>&1 | tee "$CB/logs/linux-sync.log"

# Chromium's own dependency installer lives in the tree, so it runs after the sync
sudo "$CB/chromium_git/chromium/src/build/install-build-deps.sh" --no-arm --no-chromeos-fonts --no-nacl

# Verify the pins
cd "$CB/chromium_git/chromium/src"
grep -E '^(MAJOR|MINOR|BUILD|PATCH)=' chrome/VERSION | cut -d= -f2 | paste -sd.   # 154.0.8037.58
git -C cef rev-parse HEAD                                                     # 564dd6c4aafff558…
ls build/linux | grep sysroot                                                 # the Debian sysroot gclient fetched

    An interrupted first fetch can't resume. Do what scripts/download-engine does on macOS: move the half-made src aside and rerun.

  7. Generate and build the stock baseline container · hours, CPU/RAM-bound

    source "$HOME/chromium-build/env-linux.sh"
cd "$CB/chromium_git/chromium/src/cef" && ./cef_create_projects.sh
cd "$CB/chromium_git/chromium/src"

# About 2 GB of RAM per job keeps the link steps out of swap
JOBS=$(( $(awk '/MemTotal/ {print int($2/1048576)}' /proc/meminfo) / 2 ))
[ "$JOBS" -gt "$(nproc)" ] && JOBS=$(nproc)
autoninja -C out/Release_GN_x64 -j "$JOBS" chrome chrome_sandbox \
  2>&1 | tee "$CB/logs/linux-build.log"

    The baseline is stock Chrome from the pinned tree. Bay's engine on every platform is Chrome plus Bay's layer, so this is what Phase 1 patches. CEF's tooling only fetched and generated the tree; nothing here links libcef.

  8. Run it on your desktop host · exit the container

    OUT="$HOME/chromium-build/chromium_git/chromium/src/out/Release_GN_x64"
P="$HOME/.cache/bay-baseline"                                            # a throwaway profile
"$OUT/chrome" --user-data-dir="$P" https://www.chromium.org/              # auto-selects the platform
"$OUT/chrome" --user-data-dir="$P" --ozone-platform=wayland chrome://gpu  # Wayland, check GPU
"$OUT/chrome" --user-data-dir="$P" --ozone-platform=x11 chrome://sandbox  # X11/XWayland, check sandbox
# The host Bay builds on: upstream's WebUI browser with SurfaceEmbed tabs
"$OUT/chrome" --user-data-dir="$P" --enable-features=Webium,SurfaceEmbed https://www.chromium.org/

# glibc floor of the build (decides the oldest distro Bay can support)
objdump -T "$OUT/chrome" | grep -o 'GLIBC_[0-9.]*' | sort -Vu | tail -1
    If you see "No usable sandbox"

    Stock Arch kernels allow user namespaces, so this usually means linux-hardened or a sysctl. For local testing only, use Chromium's SUID helper. Never use --no-sandbox. 

    sudo chown root:root "$OUT/chrome_sandbox" && sudo chmod 4755 "$OUT/chrome_sandbox"
export CHROME_DEVEL_SANDBOX="$OUT/chrome_sandbox"

  9. Bay-patched engine, once Phase 1 lands container · planned interface

    This command shape is planned and doesn't work yet: Phase 0 generalises scripts/windows/engine.py into one script with a platform profile, and Phase 1 adds the linux series lines. It reuses the checkout from Step 6 and keeps the Windows script's safety rules: pinned revisions, no resets, and a series.py check before every build. 

    cd "$HOME/code/bay"
python3 scripts/engine.py --platform linux prepare   # checkout → ungoogled → domain subst. → chromium series → Bay layers → gn gen
python3 scripts/engine.py --platform linux build     # chrome (as bay) with Bay's layer, chrome_sandbox
python3 scripts/engine.py --platform linux archive   # bay-engine-154.0.8037.58-linux-x64-<digest>.tar.zst + symbols

Scope

In scope for the first Linux release

  • The sidebar and tabs model: spaces, pinned and split panes, command panel, find bar, downloads, settings, developer bar and inspector
  • Chrome features through the engine: extensions and the Web Store, passwords and autofill, permissions, PiP, casting, DevTools, site settings, history, bookmarks
  • Content blocker, favicons, zoom, profiles, screen sharing through PipeWire
  • Import from Chrome, Chromium, Brave, Vivaldi, Opera, Edge and Helium for Linux, Firefox (native, snap and Flatpak profiles) and Zen
  • Encrypted folder sync, readable by the Mac, Windows and Linux apps
  • Packages, repo-based updates, default-browser registration, x86_64

Out of scope

  • Liquid Glass and vibrancy. There's no portable compositor blur. KDE's blur protocol may come later
  • The four Metal shader views at launch. Because the UI runs in Chrome, a WebGL/WebGPU port is possible later
  • Dock tile, Dock selection, alternate app icons, the global menu bar
  • AppleScript, Handoff, Apple Translation, EventKit calendar
  • Importing from Safari, Dia and Arc (none exist on Linux)
  • Flatpak at launch (see decisions), arm64 at launch

Lessons from Helium & Zen

Helium Chromium · ungoogled

The closest engine match: an ungoogled-chromium base with its own patch series.

  • Builds in a container. scripts/docker-build.sh builds a debian:trixie-slim image with a fixed package list, then runs build.sh in it. The README warns that the bare script only works on Debian with every dependency installed.
  • GN flags (flags.linux.gn): use_sysroot=true, symbol_level=1, use_vaapi=true, rtc_use_pipewire=true, is_official_build=true, use_siso=true, with sccache or ccache when available.
  • Few Linux patches: six of its own (branding, binary rename, default theme rather than GTK, middle-click paste flag, missing-desktop-file error, tab strokes) plus one from portablelinux.
  • Packaging: one tarball becomes AppImage (zsync updates), .deb through a signed APT repo with stable and prerelease channels, and .rpm through COPR. Before packaging, ldd checks for unresolved libraries. Everything is GPG-signed. x86_64 and arm64.
  • Sandbox: it ships an AppArmor profile (userns for /opt/helium/helium) that the package installs, and its AppImage AppRun offers to install one on Ubuntu 24.04+. No SUID helper in the tarball.
  • No Flatpak, "as long as it's impossible to package Chromium without breaking its sandbox".

Zen Firefox · Gecko

The closest product match (spaces, split view, glance, compact mode), on a different engine.

  • The UI runs in the engine. src/zen/* is about 178k lines of JS/CSS in Gecko's own UI layer, with only 18 Linux-specific references. Linux costs Zen almost nothing in UI code. That's the argument for the hosting choice below.
  • Glass is off on Linux. Zen uses vibrancy on macOS and Mica on Windows, but zen.widget.linux.transparency defaults to false (prefs/zen/gtk.yaml). Its frosted URL bar and compact sidebar use CSS backdrop-filter, which can blur pages only because Gecko draws pages and UI in one document. Bay's overlay is a separate view, so the same CSS can't see the page.
  • Wayland hides the global pointer. Zen's compact mode can't track the mouse outside the window on Linux (ZenMouseTrackerInternal.h: "Wayland doesn't expose it at all") and falls back to timeouts. Bay's edge peek and auto-hide toolbar have the same limit.
  • CI: Linux builds on Ubuntu 24.04 runners (x86_64 and aarch64), with PGO on x86_64.
  • Old-distro compatibility is set on purpose: MOZ_STDCXX_COMPAT=1 keeps glibc 2.28 systems working. Bay gets the equivalent from Chromium's sysroot.
  • Packaging: a tarball with Mozilla's MAR updater, plus AppImage (uruntime, zsync). Flatpak is maintained separately on Flathub.

What Bay takes from them: build in a pinned container with the Chromium sysroot. Ship tarball, AppImage, deb and rpm from one staged directory, with AUR on top. Install an AppArmor userns profile. GPG-sign everything. Keep a prerelease channel. Keep the Linux UI code close to zero by rendering the UI in the engine.

The hosting decision

Decided 17 October 2026, together with Windows: the web-rendered host (L‑W). Two constraints ruled out the alternatives. There's no maintained React Native for Linux that can host a Chromium surface, and embedding a browser in a third-party Wayland window isn't upstream in CEF (issue #2804, open since 2019). A UI that Chrome draws in Chrome's own window avoids both.

Linux-specific risk: upstream disabled SurfaceEmbedRendersRedRect on Linux (webui_browser_browsertest.cc, crbug.com/534291359). If painting fails on Wayland or X11 and the bug isn't fixed by then, try upstream's GuestContents path in the same window first, then L‑A.

Outcomes

Phase 5

Linux shell & UX

Linux

Make it feel at home on GNOME and KDE, and respect Wayland's rules rather than fighting them.

Depends on
Phase 4
Runs alongside
Phase 6
  • Frame: client-side decorations everywhere (GNOME has no server-side ones). Caption buttons follow the desktop's button layout (portal org.gnome.desktop.wm.preferences button-layout, or GTK's decoration layout), on the left or right. Check the right-docked sidebar (850c7ff) against right-hand buttons.
  • Theme: follow the Settings portal's color-scheme, accent-color and contrast. Decide whether Chrome-drawn dialogs use the default theme or GTK (Helium patches Chrome to the default theme).
  • Menus & shortcuts: the Windows app menu and Ctrl table, plus Ctrl+Q to quit and F11. Never bind Super, which the compositor owns. Use the GlobalShortcuts portal only if Bay adds global shortcuts. Chrome's portal trigger has caused repeated KDE/GNOME dialogs.
  • Type & icons: the system UI font through fontconfig (system-ui in CSS), Inter as fallback, Fluent icons.
  • Wayland window rules: apps can't place windows at absolute positions or steal focus. Tab drag-out lets the compositor place the window, session restore keeps size and maximized state only, and activation from other apps uses xdg-activation tokens. Adapt the windowing tests to match.
  • System: notifications, an XDG autostart entry, default browser through bundled xdg-settings, single instance and URL forwarding (Chrome's ProcessSingleton), file chooser (GTK or portal), trash (FreeDesktop Trash spec), reveal in folder (org.freedesktop.FileManager1.ShowItems).
  • Gestures: touchpad back/forward through Chrome's overscroll; pinch to zoom.

Exit criteria

  • Snapping and tiling work on GNOME, KDE and one wlroots compositor; fractional scaling and multi-monitor are correct.
  • Every Mac shortcut has a Linux counterpart, and the shortcuts test passes.
  • The app is usable with high contrast on and animations reduced.
Phase 6

Data: import, sync, secrets

Parsers & vectors anywhereIntegration on Linux

Someone switching from Chrome, Firefox or Zen on Linux lands in Bay with their data, and a Mac or Windows sync folder opens on Linux.

Depends on
Phase 0's C++ split; Phase 4 for integration
  • Profiles: ~/.config/{google-chrome, chromium, BraveSoftware/Brave-Browser, vivaldi, opera, microsoft-edge}; Firefox in ~/.mozilla/firefox, ~/snap/firefox/common/.mozilla/firefox and ~/.var/app/org.mozilla.firefox/.mozilla/firefox; Flatpak Chromium-family apps under ~/.var/app/*/config; Zen's own and Flatpak profiles. Find Helium's and Zen's exact profile directories in their packages.
  • Chromium secrets on Linux: v10 uses a fixed key (basic store), and v11 uses a key held in the Secret Service or KWallet under the browser's "Safe Storage" item. Linux has no app-bound encryption, so passwords and cookies can be imported after the user consents and the keyring unlocks. Firefox logins use the NSS key4.db reader that already exists.
  • Zen import: reuse the Firefox reader, then map Zen workspaces to Bay spaces (a later stretch goal).
  • Sync: the shared vault with a BoringSSL backend. Golden vectors from the Mac Swift tests must give byte-identical output. SyncKeyStore uses libsecret, and if no Secret Service is running, Bay asks for the recovery phrase each session rather than writing the key to disk.
  • Folder sync: check Nextcloud, Syncthing, Dropbox, rclone/FUSE mounts and SMB/NFS for rename atomicity and inotify limits.

Exit criteria

  • The packages/import/fixtures give identical results on Linux.
  • One shared fixture vault opens on Mac, Windows and Linux.
Phase 7

Packaging & updates

Linux + CI

One staged /opt/bay tree becomes every format, installs cleanly on Tier 1, keeps the Chromium sandbox on, and updates through the user's package manager.

Depends on
Phase 4 (an app to ship); the repos and the signing key can be set up at any time
  • Layout: /opt/bay/{bay, bay-wrapper, chrome_sandbox, chrome_crashpad_handler, resources…}, with /usr/bin/bay pointing at the wrapper. The wrapper sets CHROME_WRAPPER and the library path, as Helium's does.
  • Formats: .tar.xz, AppImage (zsync updates), .deb through a signed APT repo with stable and prerelease components, .rpm through a DNF repo or COPR, and an AUR bay-bin PKGBUILD bumped by CI.
  • Sandbox: the deb/rpm postinst installs an AppArmor profile granting userns to /opt/bay/bay (needed since Ubuntu 24.04). Keep chrome_sandbox as the SUID fallback. The AppImage's AppRun offers to install the profile.
  • Desktop integration: bay.desktop (http/https/html/pdf MIME types, New Window and New Private Window actions), AppStream metainfo, hicolor icons, native messaging host directories (~/.config/Bay/NativeMessagingHosts, /etc/bay/native-messaging-hosts).
  • Trust: GPG-sign the repos, tarball and AppImage. Linux has no OS code signing.
  • Release script: scripts/linux/release.sh, the counterpart of scripts/release.sh. It stages, runs the ldd unresolved-library check in distro containers, packs every format, and reads notes from release-notes/<version>.md.
  • Crashes: Crashpad minidumps to Bay's crash directory, plus a symbols archive per release.

Exit criteria

  • Clean VMs (Ubuntu 24.04, Debian 13, Fedora, Arch, openSUSE Tumbleweed) install, launch, become the default browser, update to the next build and uninstall cleanly.
  • chrome://sandbox shows the namespace sandbox on every Tier 1 distro, including Ubuntu with its AppArmor restriction on.
