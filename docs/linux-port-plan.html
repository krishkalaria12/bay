Bay for Linux

Linux is the third desktop target, and it differs from the other two in one important way: React Native has no usable Linux platform. Linux shares the Windows plan's host: Bay's React UI runs on react-native-web as a Chrome WebUI page, tabs are SurfaceEmbed elements in it, and the engine is NNCore, Chrome plus Bay's layer. Zen and Vivaldi are both built this way. Linux is built on top of the Windows branch and reuses its host, bridge and shared runtime. Work runs code-first: everything that can be written and checked on the Mac lands first, and building and testing on the Linux machine come last.

Summary

Yes, Bay can run on Linux, on the same host as Windows. Since 17 October 2026 the Windows plan renders Bay's UI inside the engine: the React UI runs on react-native-web as a Chrome WebUI page (chrome://bay), each tab is an <embed> backed by Chromium's SurfaceEmbed, and the engine is NNCore, which is Chrome plus Bay's layer, as on macOS. Linux uses that host unchanged. Only the window frame, the backdrop and system integration are Linux code.

Why this fits Linux. Meta ships no React Native for Linux, and the community projects are early: react-native-linux says "pre-alpha, M0 done", and react-native-gtkx has no releases. Neither can embed a Chromium surface. A UI drawn by the engine needs neither, and Chrome's own window code already runs on Wayland and X11 through Ozone. This is the model Zen uses on Gecko: about 178k lines of UI JS/CSS, of which only 18 references are Linux-specific.

Upstream is building it. Chromium's WebUI Browser (kWebium) and components/surface_embed are both in Bay's pinned tag, 154.0.8037.58, switched off by default. One caution for Linux: upstream's SurfaceEmbed render test is disabled on Linux (crbug.com/534291359) while it runs on Windows and macOS. Phase 2 tests painting on Wayland and X11 before anything else.

Built on feat/windows: the web build of the UI and its @bay/platform wrappers, the asynchronous bridge over Mojo, chrome://bay with SurfaceEmbed tab mounting, and the shared runtime (one coordinator, read-only window projections, native per-window checks) already exist there as portable sources. Linux merges that branch, turns the Windows-only switches into web-host switches, and adds its frame, notifications, secrets, data backends, engine build and packaging. See Building on feat/windows.

Order: code first, build and test last. Nothing in the shared host has run on Windows or Linux yet, and the Windows hosting gate is also still to run. Deferring the Linux build means the Linux code is written against an unverified host; the order of work keeps the Linux-only code thin so a late gate failure costs little.

Prerequisites & engine build

Do this on the Arch box when the work moves there, at the end (see Order of work). Everything runs directly on Arch, with no container. Chromium's Debian sysroot (use_sysroot=true) supplies the target libraries, so the binaries don't depend on Arch's libraries and an engine built here also runs on older distros. install-build-deps.sh only supports Debian and Ubuntu, so Step 2 installs the same dependencies with pacman.

The build in Steps 4–7 is a stock Chrome baseline with the exact pins from engine/patches/build/engine-lock.json. It proves the machine and toolchain work. The Bay-patched build uses the same checkout once Phase 1 adds linux to the series and the engine script (Step 8).

  • Flatpak at launch (see decisions), arm64 at launch

Order of work

Everything that can be written and checked on the Mac comes first. The Linux machine is used once, at the end, for the engine build, the hosting gate and the distro matrix. The phases below keep their content; this is the order they run in.

Now, on the Mac

  1. Seams (Phase 0): series platform lists, one engine script, the Linux capability column, and the shared runtime switched on by web host rather than by Windows.
  2. Host sources (Phase 3): the CSD frame view, Linux platform services, notifications, the _linux.cc engine siblings, and the is_win gates opened where the code is shared.
  3. Shared-runtime gaps: Chrome-opened windows and the utility windows, fixed on feat/windows and merged.
  4. UI (Phase 4, 5): SVG icons, caption buttons in the desktop's layout, Wayland window rules, edge peek without a global pointer.
  5. Data (Phase 6): Linux profile paths, v10/v11 secrets, the BoringSSL sync backend against the golden vectors, which run on the Mac.
  6. Packaging sources (Phase 7): the release script, deb/rpm/AppImage/AUR files, the desktop entry and the AppArmor profile.

Checks at each step: typechecks, JavaScript and portable native tests, the web build, series.py for --platform linux, and the runtime unit tests against the pinned Chromium libraries on the Mac. A Linux-target syntax check on the Mac is possible once Chromium's Debian sysroot is fetched, as the Windows branch does with mingw headers.

Last, on the Linux machine

  1. Prerequisites and engine build (steps, Phase 1).
  2. Hosting gate (Phase 2): SurfaceEmbed painting on Wayland and X11 first.
  3. Acceptance: the exit criteria of Phases 3–6 on GNOME and KDE.
  4. Packages and matrix (Phase 7, 8): clean VMs, GPUs, IME, accessibility, beta.

The cost of a late gate. If SurfaceEmbed fails on Linux (its upstream render test is disabled there), the fallback is upstream's GuestContents path or the L‑A overlay host. Both keep the UI, the bridge, the runtime and the data work; only the tab mounting and the frame change. Running the Windows gate first, when a Windows machine is free, would also catch shared host failures early.

Lessons from Helium & Zen

Helium Chromium · ungoogled

The closest engine match: an ungoogled-chromium base with its own patch series.

  • Builds in a container. scripts/docker-build.sh builds a debian:trixie-slim image with a fixed package list, then runs build.sh in it. The README warns that the bare script only works on Debian with every dependency installed.
  • GN flags (flags.linux.gn): use_sysroot=true, symbol_level=1, use_vaapi=true, rtc_use_pipewire=true, is_official_build=true, use_siso=true, with sccache or ccache when available.
  • Few Linux patches: six of its own (branding, binary rename, default theme rather than GTK, middle-click paste flag, missing-desktop-file error, tab strokes) plus one from portablelinux.
  • Packaging: one tarball becomes AppImage (zsync updates), .deb through a signed APT repo with stable and prerelease channels, and .rpm through COPR. Before packaging, ldd checks for unresolved libraries. Everything is GPG-signed. x86_64 and arm64.
  • Sandbox: it ships an AppArmor profile (userns for /opt/helium/helium) that the package installs, and its AppImage AppRun offers to install one on Ubuntu 24.04+. No SUID helper in the tarball.
  • No Flatpak, "as long as it's impossible to package Chromium without breaking its sandbox".

Zen Firefox · Gecko

The closest product match (spaces, split view, glance, compact mode), on a different engine.

  • The UI runs in the engine. src/zen/* is about 178k lines of JS/CSS in Gecko's own UI layer, with only 18 Linux-specific references. Linux costs Zen almost nothing in UI code. That's the argument for the hosting choice below.
  • Glass is off on Linux. Zen uses vibrancy on macOS and Mica on Windows, but zen.widget.linux.transparency defaults to false (prefs/zen/gtk.yaml). Its frosted URL bar and compact sidebar use CSS backdrop-filter, which can blur pages only because Gecko draws pages and UI in one document. Bay's overlay is a separate view, so the same CSS can't see the page.
  • Wayland hides the global pointer. Zen's compact mode can't track the mouse outside the window on Linux (ZenMouseTrackerInternal.h: "Wayland doesn't expose it at all") and falls back to timeouts. Bay's edge peek and auto-hide toolbar have the same limit.
  • CI: Linux builds on Ubuntu 24.04 runners (x86_64 and aarch64), with PGO on x86_64.
  • Old-distro compatibility is set on purpose: MOZ_STDCXX_COMPAT=1 keeps glibc 2.28 systems working. Bay gets the equivalent from Chromium's sysroot.
  • Packaging: a tarball with Mozilla's MAR updater, plus AppImage (uruntime, zsync). Flatpak is maintained separately on Flathub.

What Bay takes from them: build against the pinned Chromium sysroot. Ship tarball, AppImage, deb and rpm from one staged directory, with AUR on top. Install an AppArmor userns profile. GPG-sign everything. Keep a prerelease channel. Keep the Linux UI code close to zero by rendering the UI in the engine.

The hosting decision

Decided 17 October 2026, together with Windows: the web-rendered host (L‑W). Two constraints ruled out the alternatives. There's no maintained React Native for Linux that can host a Chromium surface, and embedding a browser in a third-party Wayland window isn't upstream in CEF (issue #2804, open since 2019). A UI that Chrome draws in Chrome's own window avoids both.

Linux-specific risk: upstream disabled SurfaceEmbedRendersRedRect on Linux (webui_browser_browsertest.cc, crbug.com/534291359). If painting fails on Wayland or X11 and the bug isn't fixed by then, try upstream's GuestContents path in the same window first, then L‑A.
